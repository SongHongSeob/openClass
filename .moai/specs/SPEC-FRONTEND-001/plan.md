### B.3 DEP-3 — 선행 PR 병합 (미해소 — **유일한 차단 요소이며, 0.1.0이 그 영향을 과소평가했다**)

`SPEC-ENROLLMENT-001`의 구현(`enrollment`·`waitlist` 패키지)은 **`main`에 병합되지 않았다.** 브랜치 `sync/SPEC-ENROLLMENT-001`에 있으며 PR #1로 열려 있다. 해당 SPEC의 프론트매터는 그 브랜치에서 `status: in-progress`(v0.3.0 제자리 개정 중), `main`에서는 `status: draft`다.

#### B.3.1 0.1.0의 판단이 틀렸던 지점

0.1.0은 "M1~M3은 `main`만으로 진행 가능하다"고 적었다. **코드 가용성에 관해서는 맞지만, 진입 게이트에 관해서는 틀렸다.**

이 SPEC의 프론트매터는 `depends_on: [SPEC-AUTH-001, SPEC-COURSE-001, SPEC-ENROLLMENT-001]`이다. `.claude/rules/moai/workflow/spec-workflow.md` § Depends_on Pre-flight Check는 다음을 규정한다:

- 사전 점검은 **Phase 1의 sub-step 0**으로, plan-auditor 호출보다 **먼저** 실행된다
- 충족의 정의는 의존 SPEC의 **`status: completed`** 단 하나이며, 나머지 7개 상태값은 전부 미충족이다 — **부분 인정 없음, 점수 기반 우회 없음**
- 미충족 시 사전 점검은 plan-auditor 단계로 **진행하지 않는다**

`SPEC-ENROLLMENT-001`은 `completed`가 아니다(`in-progress`). 기능적으로 얼마나 완성되었는지는 이 판정에 영향을 주지 않는다.

**따라서 게이트는 마일스톤 단위가 아니라 `/moai run` 호출 단위로 막는다. M1도 시작할 수 없다.**

#### B.3.2 선택지 2개 — 오케스트레이터/사용자가 정한다

이 SPEC은 어느 쪽도 단독으로 선택하지 않는다. 두 선택지의 실제 비용을 정직하게 적는다.

## §C 핵심 결정 — 되돌리기 어려운 순서

검토자는 이 절을 위에서부터 본다. **아래로 갈수록 되돌리기 쉽다.**

### C.1 (가장 되돌리기 어려움) 백엔드 응답 타입의 단일 선언 — `REQ-NFR-005`

**결정**: 백엔드 DTO와 1:1 대응하는 타입 모듈 하나(`src/api/types.ts`)를 두고, 모든 화면이 이를 소비한다. 화면별 중복 선언을 금지한다.

**이 결정이 가장 되돌리기 어려운 이유**: 10개 화면 전부가 이 타입을 import한다. 형태가 바뀌면 전 화면이 영향받는다.

**세부 결정 2건** (`design.md` §A.1의 근거 참조):

1. **날짜는 문자열로 수신하고 표시 직전에만 변환한다.** 백엔드 `LocalDateTime`은 타임존 없이 직렬화되므로, 즉시 `Date`로 변환하면 브라우저 로컬 타임존이 암묵 적용되어 관리자가 입력한 값과 다르게 표시될 수 있다.
2. **`status` 문자열 유니온은 미지 값을 허용하는 형태로 선언한다.** 백엔드가 결과값을 추가해도 클라이언트가 타입 오류·런타임 중단으로 무너지지 않아야 한다 (`REQ-ENR-009`).

### C.2 오류 정규화의 판정 순서 — `REQ-ERR-001`~`006`

**결정**: 단일 지점(`src/api/errors.ts`)에서 아래 **순서대로** 판정한다. 순서 자체가 계약이다.

```
1. 응답을 받지 못함 (fetch reject)      → 네트워크/차단  ※ "서버 오류"로 표시하지 않음
2. 401                                   → 세션 만료      ※ 바디 형태와 무관하게 선행 판정
3. 바디에 code 필드 존재                 → 도메인 오류    ※ code로 문구 선택
4. 그 외 (403 / 400 / 미지 형태)         → 상태코드 기반  ※ 원문 미노출
```

**2단계를 3단계보다 앞에 두는 것이 핵심 결정이다.** 401은 F1(`INVALID_CREDENTIALS` — 로그인 실패)과 F2(무토큰·만료) 두 경로에서 발생한다. code 판정을 먼저 하면 두 경우가 갈라져 **세션 폐기가 한쪽에서만 일어난다.**

**이 결정이 중요한 이유**: 백엔드 오류 바디는 3종으로 분기하며(`spec.md` §A.6), `code` 필드가 없는 두 경로(401 만료·400 검증 실패)가 하필 **사용자가 가장 자주 마주치는** 오류다. `body.code`만 읽는 순진한 구현은 가장 흔한 오류에서 "알 수 없는 오류"를 표시한다.

### C.3 폴링 스케줄과 상한 — `REQ-ENR-006`, `REQ-ENR-007`

**결정**: 경과 구간별 간격 증가 + 30초 상한 후 수동 전환.

| 경과 | 간격 | 근거 |
|---|---|---|
| 0~5초 | 1초 | 백엔드 `REQ-STS-003` 보장 구간(동시 500건 이하에서 5초 이내) |
| 5~15초 | 2초 | 보장 구간 초과 = 큐 혼잡. 빈도를 낮춰 혼잡을 가중시키지 않음 |
| 15~30초 | 3초 | 명백한 지연 — 화면에 지연 중 표시 |
| 30초 초과 | **중단** | 자동 폴링 종료, 수동 재확인 수단 제공 |

**30초 = 백엔드 보장치의 6배.** 이 시점에도 `PENDING`이면 정상 지연이 아니라 큐 정체·워커 이상을 의심할 상황이며, 계속 두드리는 것은 도움이 되지 않는다.

**종단 판정은 화이트리스트가 아니라 `PENDING`의 여집합이다** (`design.md` §A.2). 백엔드가 결과값을 추가해도 미지 값이 자동으로 종단 취급되어 **무한 폴링이 구조적으로 발생하지 않는다.**

**상한 도달 후에도 요청 식별자를 유지한다.** 사용자가 수동 재확인 시 같은 식별자로 조회하며 새로 접수하지 않는다 — 재접수하면 백엔드 `REQ-WRK-007` 중복 검사에 걸려 `REJECTED`가 된다.

**경과 시간의 기준점은 요청 식별자와 함께 보존한다** (`REQ-ENR-011`). 위 표 전체가 "접수 시점으로부터의 경과"에 의존하는데, `design.md` §A.6이 요청 상태 화면을 `/requests/:requestId` 경로로 정의하므로 **새로고침과 주소 직접 진입이 일급 경로**다. 식별자는 URL에 있어 살아남지만 접수 시각을 메모리에만 두면 소실되고, 그러면:

- 스케줄이 새로고침마다 1초 간격에서 다시 시작된다
- 30초 상한이 초기화되어 **사용자가 새로고침을 반복하는 것만으로 정체된 요청을 영구히 고빈도 폴링 상태로 유지**할 수 있다 — `REQ-ENR-006`이 막으려 한 혼잡 가중이 그대로 발생한다

따라서 접수 시각을 식별자와 **같은 수명·같은 저장소**에 둔다. 구체 저장 수단은 run 단계가 정하되, 판정 기준은 하나다 — **새로고침 후에도 상한이 최초 접수 시점부터 측정되는가.** `AC-FE-073a`(자동 — 보존된 접수 시각 기준 스케줄 재계산)와 `AC-FE-073b`(수동 — 브라우저 새로고침으로 동일 동작 재현)가 이를 검증한다.

### C.4 토큰 저장 위치 — `sessionStorage` (`REQ-SES-004`)

**결정**: `sessionStorage`. 백엔드의 **실제 능력**에 정합시킨 선택이다.

확인된 백엔드 조건: denylist 없음(서버가 토큰을 무효화할 수단 없음) · 리프레시 토큰 회전 없음 · TTL 30분 · CSRF 비활성이며 **그 근거가 "쿠키 자격 증명을 쓰지 않는다"**(`SecurityConfig` 주석).

| 후보 | 판정 |
|---|---|
| `localStorage` | **기각.** 서버가 무효화할 수 없는 자격 증명이 디스크에 무기한 잔류 — 백엔드 조건과 최악의 조합 |
| 메모리 전용 | **기각.** 새로고침마다 세션 소실 → "클릭하며 확인"이 목적인 SPEC에서 심각한 마찰. XSS는 메모리 토큰도 읽으므로 방어 효과도 통념만큼 크지 않음 |
| **`sessionStorage`** | **채택.** 탭 단위 격리 + 탭 종료 시 소멸 → 노출 창이 탭 수명으로 제한되어 30분 TTL과 정합. README의 "로그아웃 = 클라이언트가 토큰을 버림" 모델과 일치. 새로고침은 견딤 |
| `httpOnly` 쿠키 | **기각.** 보안상 최강이나 백엔드 변경 필수(Set-Cookie)이며, 쿠키 자격 증명이 생기면 CSRF 비활성 근거가 무너져 CSRF 방어를 재도입해야 함. 범위 이탈 + 부작용 과대 |

**정직한 한계 표기**: `sessionStorage`는 XSS 방어가 아니다. 탭이 열린 동안의 노출은 `localStorage`와 동일하며, 얻는 것은 **지속 기간의 축소**뿐이다. 실질적 완화는 백엔드의 30분 TTL이다. 이 한계를 `spec.md` REQ-SES-004 근거 주석에 기록했다.

### C.5 개발 서버 오리진 정렬 — Vite 프록시는 **채택하지 않는다**

0.1.0은 `DEP-1`(CORS 미설정) 우회 수단으로 Vite 개발 서버 프록시를 채택했다. **`DEP-1`이 해소되어(§B.1) 그 전제가 사라졌으므로 이 결정을 뒤집는다.**

**결정: 프록시를 도입하지 않는다. 개발 서버를 백엔드가 허용하는 오리진(기본 `http://localhost:5173`)으로 띄워 브라우저가 직접 교차 오리진 호출을 수행한다.**

채택 근거:

1. **단순성 사다리.** 백엔드가 이미 제공하는 능력(CORS 허용)으로 해결되는 것을 개발 서버 설정 표면을 추가해 다시 풀 이유가 없다. Vite 기본 포트가 백엔드 기본 허용 오리진과 **이미 일치**하므로 추가 설정이 0이다.
2. **이 SPEC의 목적에 정합.** 목적은 "실제로 동작함을 확인"하는 것이다. 프록시는 브라우저가 보기에 동일 오리진을 만들어 **CORS 경로를 검증 대상에서 제거한다** — 즉 확인해야 할 것을 확인하지 않게 만든다. 프록시 없이 띄우면 preflight·허용 헤더·허용 메서드가 실제로 동작하는지가 **개발 첫 화면에서 즉시 드러난다.**
3. **AP-6이 경고하던 함정 자체가 소멸.** "프록시로 개발했는데 배포하니 전부 실패"는 프록시를 쓰지 않으면 발생할 수 없다.

**남는 위험과 그 처리** — 프록시를 버린 대가로 오리진 정렬이 운영 조건이 된다:

| 상황 | 결과 | 처리 |
|---|---|---|
| 개발 서버가 5173으로 뜸 | 정상 동작 | 기본 경로 |
| 5173이 점유되어 Vite가 다른 포트로 자동 이동 | **전 호출 CORS 차단** | `REQ-ERR-005`가 이를 "네트워크/차단"으로 분류해 표시하므로 원인 오인이 방지된다. 백엔드를 `CORS_ALLOWED_ORIGINS`와 함께 기동하거나 Vite 포트를 고정한다 |
| 빌드 산출물을 다른 오리진에서 서빙 | 차단 | 해당 오리진을 `CORS_ALLOWED_ORIGINS`에 추가 (백엔드 기동 설정 — 소스 변경 아님) |

> 프록시를 **금지**하는 것은 아니다. 위 상황을 회피하기 위해 개발자가 로컬에서 프록시를 켜는 것은 자유다. 다만 **이 SPEC의 산출물에 프록시 설정을 포함하지 않으며**, `REQ-NFR-007`의 수동 시나리오 확인은 **프록시 없이** 수행한다 — 그래야 확인한 것이 실제 배치 조건과 같아진다.

### C.6 라이브러리 선택 (단순성 사다리 적용)

프로젝트 헌장의 **단순성 사다리**(재사용 → 표준 라이브러리 → 플랫폼 기본 → 기존 의존성 → 최소 코드)를 적용했다. 사용자가 확정한 것은 React + Vite + TypeScript 세 가지뿐이며 나머지는 이 SPEC이 결정한다.

| 영역 | 결정 | 사다리 단계 | 근거 요약 |
|---|---|---|---|
| **라우팅** | **React Router** | 4 (신규 의존성) | 화면 10개의 평범한 다중 화면 SPA. 경로 가드를 중첩 라우트로 자연스럽게 표현. 라우터 없이는 뒤로가기·직접 진입(`REQ-ADM-002` 검증 대상)이 성립하지 않음. TanStack Router는 타입 안전이 강점이나 이 규모에서 학습 비용이 목표와 상충 |
| **HTTP 클라이언트** | **표준 `fetch` + 얇은 래퍼** | 3 (플랫폼 기본) | 필요한 것은 기준 주소 결합·Bearer 부착·오류 정규화 3가지뿐. axios를 넣어도 `REQ-ERR-002`의 단일 지점 래퍼는 어차피 필요하므로 의존성만 늘어남 |
| **서버 상태·폴링** | **TanStack Query** | 4 (신규 의존성) | **이 SPEC에서 사다리 4단계를 정당화하는 유일한 항목.** 폴링 요구(종단 시 즉시 중단·간격 증가·상한 후 수동 전환·언마운트 정리·401 예외)를 `useEffect`+`setTimeout`으로 직접 구현하면 타이머 중복·정리 누락 결함이 발생하기 쉬운데, **이 SPEC의 목적이 "시스템이 실제로 동작함을 확인"하는 것**이므로 확인 도구 자체에 결함이 있으면 목적이 훼손된다. `refetchInterval`의 함수 형태가 "직전 데이터를 보고 다음 간격 결정 또는 `false` 반환으로 중단"을 선언적으로 표현 |
| **클라이언트 상태** | **React Context + `useReducer`** | 3 (React 기본) | 전역 공유가 필요한 클라이언트 상태는 **세션 하나**(`{accessToken, email, role, exp}`). 서버 데이터는 전부 위 항목이 관리. Redux/Zustand는 이 규모에서 순비용 |
| **폼** | **제어 컴포넌트 + 소형 검증 헬퍼** | 5 (최소 코드) | 폼 4개(회원가입·로그인·강좌 생성·수정), 각 5필드 이하. **검증의 진실 원천은 백엔드**(`@Valid` → 400)이므로 클라이언트 검증은 왕복을 줄이는 편의일 뿐 권위가 없음 |
| **스타일링** | **CSS Modules** | 4 (Vite 기본 지원, 신규 의존성 없음) | Vite가 `*.module.css`를 무설정 처리. **이 SPEC의 성공 기준에 시각적 완성도 항목이 하나도 없다.** Tailwind는 빌드 설정 표면과 클래스 관습을 추가. 스타일링은 **가장 되돌리기 쉬운 결정**이므로 후속 SPEC이 재검토하도록 남김 |

> 신규 의존성은 **React Router · TanStack Query 2개뿐**이다. 나머지는 전부 플랫폼/프레임워크 기본 기능으로 해결했다.

### D.1 테스트 전략에 관한 단서

`REQ-NFR-007`이 요구하는 것은 **사람에 의한 수동 시나리오 확인**이며 브라우저 자동화 도구(Playwright 등) 도입이 **아니다** (`spec.md` §D "Out of Scope — 인프라 및 배포").

TDD 대상은 **순수 로직 단위**다:

- 오류 정규화 판정 순서 (§C.2) — 3종 바디 × 상태 코드 조합
- 폴링 스케줄 계산 (§C.3) — 경과 시간 → 간격, **종단 판정(`PENDING` 여집합 — 미지 문자열 입력 포함)**, **접수 시각 기준 상한 측정(`REQ-ENR-011`)**
- JWT 페이로드 디코드 및 만료 판정 (`design.md` §A.5)
- 세션 수립·복원·폐기 전이
- **목록 응답 → 화면 모델 변환** — 빈 배열이 "내역 없음"으로 매핑되는가(`REQ-CNL-007`), 대기 항목의 취소 식별자로 `waitlistEntryId`가 선택되는가(`REQ-CNL-003`)

  > 마지막 항목이 자동 테스트 대상인 이유: `waitlistEntryId`와 `position`은 둘 다 `Long`이라 **타입 검사가 혼동을 잡아 주지 못하고**, 화면상으로도 취소가 성공한 것처럼 보인다(엉뚱한 본인 소유 행이 취소되므로 오류조차 나지 않는다). 사람의 조작으로는 발견하기 어렵고 자동 테스트로는 쉽게 잡히는 전형적 사례다.

**화면 컴포넌트의 렌더링 테스트는 이 SPEC의 필수 범위가 아니다** — 확인 수단이 사람의 조작이기 때문이다. 위 4개 로직은 사람이 눈으로 검증하기 어려운 영역이므로 자동 테스트가 실질적 가치를 갖는다.

**진입 조건**: `DEP-3` 처리 방침 확정 (§B.3 선택지 A 또는 B)
**완료 판정**: E1~E4 통과 + 오류 정규화 단위 테스트 통과 + **브라우저에서 `GET /api/courses`가 프록시 없이 교차 오리진으로 성공** (CORS 실동작 확인 — §C.5)

> 0.1.0 대비 축소: Vite 프록시 설정이 이 마일스톤에서 빠졌다(`DEP-1` 해소로 불필요, §C.5). 대신 **CORS 실동작 확인**이 완료 판정에 추가되었다 — 프록시로 가려져 있던 경로를 실제로 검증한다.

> **주의**: `@Valid` 실패 응답의 정확한 바디 형태는 `research.md` §7-1이 **미확인 항목**으로 기록했다. 이 마일스톤에서 **실제 응답을 관측하여 확정**한 뒤 정규화 로직을 확정한다.

### M6 — 취소 (우선순위: 중) — **`DEP-2` 해소로 차단 해제됨**

**포함**: 내 수강신청 목록(§A.4 13번), 내 대기명단 목록(14번), 확정 취소(7번 — 202→폴링), 대기 취소(8번 — 200 동기).

**대상 요구사항**: `REQ-CNL-001`~`009`

**진입 조건**: M4 완료 (`DEP-2` 차단 조건은 제거됨 — §B.2). `DEP-3`는 M4와 공유하는 조건이므로 M4를 통과했다면 이미 충족되어 있다.

**구현 시 반드시 지킬 5가지** (전부 `DEP-2` 해소 후 새로 드러난 계약 — 0.1.0에는 없던 내용):

1. **경로** — `GET /api/enrollments/mine`, `GET /api/waitlist-entries/mine`. 0.1.0이 §B.2에 적어 둔 제안 경로는 **존재하지 않는다.**
2. **대기 취소 식별자는 `waitlistEntryId`** — `position`이 아니다. 둘 다 `Long`이라 타입 검사가 잡아 주지 않으며, 혼동하면 **엉뚱한 행이 조용히 취소**된다(INV-FE-009).
3. **빈 배열은 오류가 아니다** — 0건이면 `200` + `[]`. 신규 회원의 첫 진입이 항상 이 상태이므로, 오류로 처리하면 **가장 흔한 정상 상태가 오류로 표시**된다(INV-FE-010).
4. **정렬을 재구성하지 않는다** — 확정은 `enrollmentId` 오름차순, 대기는 `position` 오름차순. 백엔드 순서가 결정적이므로 클라이언트가 재정렬하면 표시 순서가 응답과 어긋나 AC-FE-110의 대조 대상이 사라진다.
5. **`position`을 전역 대기 순위로 표시하지 않는다** — `position`은 **그 항목이 속한 강좌 안에서의 순번**이다(백엔드 `nextPosition`이 `WHERE courseId = :courseId`로 계산하며, 부분 유니크 인덱스도 `(course_id, position)`이다). 여러 강좌에 대기 중인 회원의 목록을 `position` 오름차순으로 늘어놓아도 그것은 **승격 예정 순서가 아니다** — 강좌별 대기열은 각 강좌의 정원 변동에 따라 독립적으로 진행한다. 화면은 `position`을 반드시 `courseTitle`과 나란히 렌더링하고, "승격 예정 순서"·"내 대기 순위" 같은 전역 순위를 뜻하는 표기를 쓰지 않는다(`REQ-CNL-008` 주의 항목, INV-FE-004 계열).

**완료 판정**: 두 취소 화면 완주 + 목록 조회 응답의 식별자만으로 취소가 성립함 확인(추측·열거 0건) + 보유 내역 0건 계정에서 오류가 아닌 "내역 없음" 표시 확인 + 타인 대상 취소 시도가 403/404로 차단되고 소유자 존재 여부를 추측할 수 없음 확인

### M7 — 수동 시나리오 확인 (우선순위: 최상 — 이 SPEC의 존재 이유)

**진입 조건**: M2~M6 완료 (`DEP-2` 해소로 M6의 조건부 성격이 사라져 M6도 필수 선행이 되었다)

**시나리오 표** (사람이 브라우저에서 직접 수행 — **프록시 없이 실제 오리진에서**, §C.5):

| # | 시나리오 | 기대 |
|---|---|---|
| S1 | 회원가입 → 로그인 → 목록 → 상세 → 신청 → 결과 표시 | 완주 |
| S2 | 정원 찬 강좌 신청 | `WAITLISTED` + 대기 순번 표시 |
