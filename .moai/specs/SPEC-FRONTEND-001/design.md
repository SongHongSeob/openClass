# SPEC-FRONTEND-001 — 설계 (design)

> `spec.md`가 **무엇을·왜**를 정한다면, 이 문서는 **어떻게**의 구조적 골격을 정한다. 파일 단위 구현 세부는 run 단계의 소유이며, 여기서는 되돌리기 어려운 구조적 결정만 기록한다.

---

## §A 구조 결정 — 되돌리기 어려운 순서로

이 절은 **변경 가능성이 높은 결정을 먼저** 배치한다. 아래로 갈수록 기계적이고 되돌리기 쉽다.

### A.1 데이터 형태 — 백엔드 응답 타입의 단일 선언 지점

`REQ-NFR-005`가 요구하는 "타입 정의 단일 지점"의 구체적 형태를 정한다. 이 결정이 가장 되돌리기 어렵다 — 모든 화면이 이 타입을 소비하므로 형태가 바뀌면 전 화면이 영향받는다.

**결정: 백엔드 DTO와 1:1 대응하는 타입 모듈 하나를 두고, 화면 전용 파생 타입은 그로부터 유도한다.**

대응 관계는 다음과 같이 고정한다 (백엔드 레코드 → 클라이언트 타입):

| 백엔드 레코드 | 클라이언트 타입 | 비고 |
|---|---|---|
| `SignupResponse(id, email, role)` | `SignupResult` | `role`은 `"USER" \| "ADMIN"` 유니온 |
| `LoginResponse(accessToken)` | `LoginResult` | |
| `CourseResponse(...9 fields)` | `Course` | `startsAt`/`endsAt`는 문자열로 수신 후 표시 시점에 변환 |
| `CoursePageResponse(items, totalElements, totalPages, currentPage)` | `CoursePage` | |
| `EnrollmentReceiptResponse(requestId)` | `Receipt` | 접수·취소 공통 |
| `EnrollmentStatusResponse(requestId, status, waitlistPosition)` | `RequestStatus` | `status`는 §A.2의 유니온 |
| `EnrollmentListItemResponse(enrollmentId, courseId, courseTitle, status, enrolledAt)` | `EnrollmentListItem` | `enrolledAt`은 문자열로 수신 후 표시 시점 변환. `status`는 `'ENROLLED'` 고정(백엔드가 활성 행만 반환) |
| `WaitlistListItemResponse(waitlistEntryId, courseId, courseTitle, position, status)` | `WaitlistListItem` | **`waitlistEntryId`와 `position`을 구조적으로 구별한다 — 아래 참조** |
| `ErrorResponse(code, message)` | (직접 노출하지 않음 — §A.3의 정규화 형태로만 소비) | |

**`waitlistEntryId`와 `position`의 혼동을 타입 층위에서 막는다.** 두 값은 백엔드에서 모두 `Long`이므로 클라이언트가 둘 다 `number`로 선언하면 **컴파일러가 뒤바꿈을 잡아 주지 못한다.** 이 SPEC의 취소 경로는 그 뒤바꿈이 오류를 내지 않고 **엉뚱한 본인 소유 행을 조용히 취소**하는 형태로 실패하므로(INV-FE-009), 타입만으로 방어할 가치가 있다.

구체 수단은 run 단계가 정하되(브랜디드 타입·별칭 타입·래퍼 중 택일), **판정 기준은 하나다 — `position`을 취소 함수의 인자로 넘기는 코드가 타입 검사에서 거부되는가.** 사다리 관점에서 이는 "최소 코드"(5단계)로 해결되는 항목이며 새 의존성이 필요 없다.

두 목록 타입에는 **빈 배열이 정상값**임이 반영되어야 한다 — 옵셔널·nullable로 선언하여 "없음"을 별도 상태로 만들지 않는다. 빈 배열과 미조회 상태를 같은 형태로 표현하면 §A.3의 오류 분류와 뒤섞여 `REQ-CNL-007`을 위반하기 쉽다.

**`status` 필드를 문자열 유니온으로 선언하되, 알 수 없는 값을 허용하는 형태로 둔다.** 백엔드가 향후 결과값을 추가해도 클라이언트가 타입 오류나 런타임 중단으로 무너지지 않아야 한다(`REQ-ENR-009`).

**날짜를 문자열로 유지하는 이유**: 백엔드 `LocalDateTime`은 타임존 정보 없이 직렬화된다. 클라이언트가 이를 `Date`로 즉시 변환하면 브라우저 로컬 타임존이 암묵적으로 적용되어, 표시 값이 관리자가 입력한 값과 달라질 수 있다. 수신 시점에는 문자열로 두고 **표시 직전에만** 변환하며, 변환 규칙을 한 곳에 모은다.

### A.2 상태 도메인 — 클라이언트가 해석해야 할 값 집합

`SPEC-ENROLLMENT-001` §A.4가 정의한 클라이언트 노출 상태값을 그대로 수용한다. 클라이언트는 이 집합을 **재정의하지 않고 소비만** 한다.

| 상태값 | 종단 | 화면 의미 |
|---|---|---|
| `PENDING` | 아니오 | 처리 중 — 폴링 계속 |
| `SUCCESS` | 예 | 수강신청 확정 |
| `WAITLISTED` | 예 | 대기명단 등록 — 순번 함께 표시 |
| `CLOSED` | 예 | 강좌 모집 마감으로 처리 불가 |
| `REJECTED` | 예 | 중복 신청 등 요청이 유효하지 않음 |
| `FAILED` | 예 | 처리 중 오류 — 재시도 안내 |
| `CANCELLED` | 예 | 취소 완료 (취소 요청의 결과) |
| `PROMOTED` | 예 | 정원 증설로 승격 처리됨 |
| `NOOP` | 예 | 승격 대상 없음 |

**종단 판정 규칙: `PENDING`이 아닌 모든 값은 종단이다.** 이 규칙을 유지하면 백엔드가 결과값을 추가해도 클라이언트가 무한 폴링에 빠지지 않는다 — 미지의 값도 자동으로 종단으로 취급되어 폴링이 멈춘다. 종단 목록을 나열해 대조하는 방식(화이트리스트)은 미지 값에서 폴링이 멈추지 않으므로 채택하지 않는다.

> 이것은 INV-FE-002(종단 도달 후 호출 없음)를 미래 변경에 대해서도 성립시키는 설계다.

### A.3 오류 정규화 — 3종 → 1종 변환의 판정 순서

`REQ-ERR-001`~`006`의 구조적 구현. **판정 순서가 곧 계약**이므로 여기에 고정한다.

정규화 결과 형태는 세 요소를 갖는다: **분류**(사용자에게 무엇을 안내할지), **표시 문구**, **원인 코드(있으면)**.

판정 순서:

```
1. 요청이 응답을 받지 못했는가? (fetch 자체가 reject)
   → 분류 = 네트워크/차단.  REQ-ERR-005가 요구하는 구별 지점.
      이 분류는 "서버 오류"로 표시하지 않는다.

2. 응답 상태가 401인가?
   → 분류 = 세션 만료.  REQ-SES-007의 세션 폐기 흐름을 촉발한다.
      바디 형태(F1/F2)와 무관하게 401은 항상 이 분류로 앞당겨 판정한다.

3. 응답 바디에 code 필드가 있는가?  (F1)
   → 분류 = 도메인 오류.  code 값으로 안내 문구를 선택한다.

4. 그 외  (F2 403 / F3 400 / 미지의 형태)
   → 분류 = 상태코드 기반.  HTTP 상태로 안내 문구를 선택한다.
      백엔드 원문 바디는 사용자에게 노출하지 않는다 (REQ-ERR-006).
```

**2단계를 3단계보다 앞에 두는 이유**: 401은 F1(`INVALID_CREDENTIALS` — 로그인 실패)과 F2(무토큰·만료) 두 경로에서 모두 발생한다. 만약 code 판정을 먼저 하면 로그인 실패는 도메인 오류로, 만료는 상태코드 기반으로 갈라져 **세션 폐기 처리가 한쪽에서만 일어난다.** 401을 먼저 잡되, 로그인 화면에서 발생한 401은 세션이 애초에 없으므로 폐기가 무해하다.

**안내 문구 매핑은 코드/상태값별 표 하나로 관리한다.** 화면마다 문구를 흩어 두면 REQ-ERR-002(단일 지점)를 위반한다.

### A.4 폴링 스케줄 — 간격과 상한

`REQ-ENR-006`(경과에 따른 간격 증가)과 `REQ-ENR-007`(상한 도달 시 자동 중단)의 구체 값.

**근거가 되는 백엔드 보장**: `REQ-STS-003` — 동시 접수 500건 이하 부하에서 **접수부터 종단 확정까지 5초 이내**. 이 상한을 넘는 부하에서는 지연이 큐 깊이에 비례해 증가한다.

이로부터 도출한 스케줄:

| 경과 구간 | 간격 | 근거 |
|---|---|---|
| 0 ~ 5초 | 1초 | 정상 범위. 백엔드 보장 구간이므로 촘촘히 확인해 체감 지연을 최소화한다 |
| 5 ~ 15초 | 2초 | 보장 구간을 넘었다 = 큐가 혼잡하다. 빈도를 낮춰 혼잡을 가중시키지 않는다 |
| 15 ~ 30초 | 3초 | 명백한 지연. 사용자에게 지연 중임을 표시한다 |
| 30초 초과 | 중단 | 자동 폴링 종료. 수동 재확인 수단 제공 (REQ-ENR-007) |

**30초를 상한으로 정한 이유**: 백엔드 보장(5초)의 6배다. 이 시점에도 `PENDING`이면 정상 범위의 지연이 아니라 **큐 정체나 워커 이상**을 의심해야 하는 상황이며, 클라이언트가 계속 두드리는 것은 도움이 되지 않는다. 사용자에게 통제권을 넘기는 것이 정직하다.

**요청 식별자는 상한 도달 후에도 유지된다** — `REQ-ENR-007`의 명시 요구. 사용자가 수동 재확인을 누르면 같은 식별자로 조회하며, 새 요청을 접수하지 않는다. (새로 접수하면 백엔드 `REQ-WRK-007`의 중복 검사에 걸려 `REJECTED`가 된다.)

**경과 시간의 기준점(접수 시각)도 식별자와 함께 보존한다** — `REQ-ENR-011`. 위 표 전체가 "접수 시점으로부터의 경과"에 의존하는데, §A.6이 요청 상태 화면을 `/requests/:requestId` 경로로 정의하므로 새로고침과 주소 직접 진입이 **일급 경로**다. 식별자는 URL에 있어 살아남지만 접수 시각을 컴포넌트 상태에만 두면 마운트마다 재설정된다.

그 결과는 단순한 부정확이 아니다 — 스케줄이 새로고침마다 1초 간격으로 되돌아가고 30초 상한이 초기화되므로, **사용자가 새로고침을 반복하는 것만으로 정체된 요청을 영구 고빈도 폴링 상태로 유지**할 수 있다. `REQ-ENR-006`이 "큐가 혼잡할수록 빈도를 낮춘다"로 막으려 한 상황에서 정확히 반대로 동작한다.

**저장 위치는 요청 식별자와 같은 수명을 갖는 곳이어야 한다.** 식별자가 URL에 있고 세션이 `sessionStorage`에 있으므로, 접수 시각도 `sessionStorage`에 `requestId`를 키로 기록하는 것이 수명·격리 범위 양쪽에서 정합한다(탭 단위 격리, 탭 종료 시 소멸). 구체 형태는 run 단계가 정하되 판정 기준은 하나다 — **새로고침 후에도 상한이 최초 접수 시점부터 측정되는가**(AC-FE-073a 자동 · AC-FE-073b 수동).

**폴링 라이브러리의 자체 재시도와 401의 관계를 명시적으로 배선한다.** TanStack Query의 `retry` 옵션은 기본적으로 실패를 재시도하는데, `REQ-ENR-010`은 네트워크 오류는 재시도하되 **401은 재시도하지 않고 세션 폐기로 넘긴다.** 따라서 401 예외는 §A.3의 정규화 순서만으로는 부족하고 `retry` 조건 함수에도 반영되어야 한다 — 정규화가 "세션 만료"로 분류하더라도 재시도 계층이 그 전에 같은 요청을 반복하면 만료된 토큰으로 불필요한 401을 여러 번 유발한다.

**폴링 중 401 처리**: `REQ-ENR-010`이 명시하듯 401은 재시도 대상이 아니다. §A.3 판정 2단계가 세션 폐기를 촉발하고 폴링은 종료된다.

### A.5 세션 관리 — 수립·복원·폐기

```
[수립]  로그인 200 수신
          → 토큰을 sessionStorage에 기록
          → 토큰 페이로드를 base64url 디코드하여 role·exp·sub 추출 (서명 검증 없음)
          → 메모리 상태에 반영

[복원]  앱 최초 렌더 시 sessionStorage 조회
          → 토큰이 있으면 페이로드 디코드
          → exp가 이미 지났으면 즉시 폐기 (서버 왕복 불필요)
          → 유효하면 세션 복원

[폐기]  (a) 사용자 로그아웃  (b) 임의 API의 401 응답  (c) 복원 시 exp 경과
          → sessionStorage에서 제거 + 메모리 상태 초기화
```

**디코드 실패를 폐기로 처리한다.** 손상된 토큰·형식 위반 토큰은 어차피 백엔드가 401을 낼 것이므로, 클라이언트가 먼저 폐기하는 것이 사용자를 401 왕복에 노출시키는 것보다 낫다.

**`exp` 선제 확인의 성격**: 이는 편의이지 보안이 아니다. `exp`를 조작해도 서명이 맞지 않아 백엔드가 401을 낸다. `spec.md` §A.7의 원칙이 여기에도 적용된다.

### A.6 경로 구성과 가드

| 경로 | 접근 | 화면 |
|---|---|---|
| `/` | 공개 | 강좌 목록 |
| `/courses/:id` | 공개 | 강좌 상세 (+ 인증 시 수강신청 조작) |
| `/signup` | 공개 | 회원가입 |
| `/login` | 공개 | 로그인 |
| `/requests/:requestId` | 인증 | 요청 상태 (폴링 화면) |
| `/me/enrollments` | 인증 | 내 수강신청 (`DEP-2` 해소로 차단 해제) |
| `/me/waitlist` | 인증 | 내 대기명단 (`DEP-2` 해소로 차단 해제) |
| `/admin/courses` | `ADMIN` | 관리자 강좌 목록 |
| `/admin/courses/new` | `ADMIN` | 강좌 생성 |
| `/admin/courses/:id/edit` | `ADMIN` | 강좌 수정 (정원 증설 포함) |

가드는 **두 계층**이다:

1. **인증 가드** — 세션 부재 시 로그인으로 유도 (`REQ-SES-009`)
2. **역할 가드** — 세션은 있으나 `role !== "ADMIN"`이면 권한 없음 안내 (`REQ-ADM-002`)

두 계층을 분리하는 이유: 세션 없는 사용자에게 "권한 없음"을 보여주면 로그인하면 될 일을 막힌 것으로 오해한다. 반대로 일반 회원에게 로그인 화면을 보여주면 이미 로그인한 사용자가 혼란스럽다.

**가드가 보안이 아님을 코드에 남긴다.** `REQ-ADM-003`이 명시적으로 요구하는 사항이므로, 가드 구현부에 그 취지를 주석으로 기록한다.

## §B 개발 환경 구성

### B.1 개발 서버 오리진 정렬 — 백엔드 CORS 설정이 고정한 제약

`DEP-1`은 해소되었다(`plan.md` §B.1). 백엔드가 CORS를 설정했으므로 브라우저가 **직접 교차 오리진 호출**을 수행할 수 있고, `plan.md` §C.5가 Vite 프록시를 채택하지 않기로 결정했다. 그 대가로 아래 백엔드 설정값이 프론트엔드의 개발·배치 조건이 된다.

**백엔드가 고정한 CORS 설정 (`SecurityConfig.corsConfigurationSource` + `application.properties`)**:

| 항목 | 값 | 프론트엔드에 대한 함의 |
|---|---|---|
| 허용 오리진 | `${CORS_ALLOWED_ORIGINS:http://localhost:5173}` | 개발 서버 포트를 **5173으로 고정**한다. Vite가 포트 충돌로 자동 이동하면 전 호출이 차단되므로, `vite.config.ts`에서 포트를 고정하고 **자동 이동을 비활성화**한다 (`strictPort` 계열 설정) — 조용히 다른 포트로 뜨는 것보다 명시적으로 실패하는 편이 원인 파악이 빠르다 |
| 허용 헤더 | `Authorization`, `Content-Type` **2종만** | 임의의 커스텀 요청 헤더(추적 ID·클라이언트 버전 등)를 추가하면 **preflight에서 조용히 실패**한다. §A.8의 `client.ts`는 이 2종 외의 헤더를 붙이지 않는다 |
| 허용 메서드 | `GET`·`POST`·`PATCH`·`DELETE`·`OPTIONS` | §A.4의 14개 엔드포인트가 쓰는 메서드는 전부 포함된다. 제약이 되지 않는다 |
| `allowCredentials` | `false` (고정) | 쿠키·자격 증명 기반 요청이 불가능하다. `fetch`의 `credentials` 옵션을 `include`로 설정하면 **브라우저가 응답을 차단**한다 — 기본값(`same-origin`)을 유지한다. §C.4가 `httpOnly` 쿠키를 기각한 근거를 백엔드가 독립적으로 확증한다 |

**포트가 어긋났을 때의 화면 동작**: `REQ-ERR-005`가 요구하는 "네트워크/차단" 분류가 이 상황을 담당한다. CORS 차단은 `fetch`가 reject되는 형태로 나타나므로 §A.3의 판정 1단계에 걸리며, 화면은 이를 "서버 오류"가 아니라 "서버에 도달하지 못함"으로 표시한다. 이 구별이 없으면 개발자가 백엔드 로직을 잘못 의심하며 시간을 낭비한다.

**다른 오리진에서 서빙해야 할 때**: 백엔드 기동 시 `CORS_ALLOWED_ORIGINS` 환경 변수에 해당 오리진을 넣는다. 이는 **백엔드 소스 변경이 아니라 기동 설정**이므로 `REQ-NFR-002`(백엔드 소스 무수정)에 저촉되지 않는다.

### B.2 API 기준 주소 주입

`REQ-NFR-003`에 따라 환경 변수로 주입한다. 프록시를 쓰지 않으므로(§B.1) 개발 환경에서도 **백엔드의 절대 주소**가 기준 주소가 된다. 다만 프론트엔드와 백엔드를 같은 오리진에서 서빙하는 배치도 가능해야 하므로, **기준 주소가 빈 문자열이어도 동작**하는 형태로 결합 규칙을 정한다(빈 문자열이면 상대 경로 호출이 되어 동일 오리진 배치가 성립한다).

### B.3 확인 계정 준비

`REQ-NFR-007`의 수동 시나리오 확인에는 두 종류의 계정이 필요하다:

- **관리자** — 백엔드 `AdminSeeder`가 `ADMIN_EMAIL`/`ADMIN_PASSWORD` 환경 변수로 최초 기동 시 자동 생성한다. 프론트엔드가 관리자 계정을 만들 수단은 없다(회원가입은 항상 일반 역할)
- **일반 회원** — 프론트엔드 회원가입 화면으로 생성한다. 이것 자체가 시나리오 1번의 시작점이다

## §C 검토했으나 채택하지 않은 설계

### C.1 낙관적 UI (접수 즉시 성공 표시)

접수 202 직후 "신청 완료"를 표시하고 폴링 결과로 정정하는 방식. **기각** — `REQ-ENR-002`가 금지하며, 정원이 찬 강좌에서는 정정이 거의 항상 발생해 화면이 자기 자신을 뒤집는다. 이 SPEC의 목적이 시스템 동작의 **정확한 관측**이므로, 화면이 사실보다 앞서가서는 안 된다.

### C.2 전역 상태 저장소에 서버 데이터 보관

강좌 목록·상태를 전역 상태로 관리하는 방식. **기각** — 서버 데이터의 신선도·재검증·중복 요청 제거를 직접 구현하게 되며, `research.md` §6.3에서 채택한 서버 상태 도구(TanStack Query)가 이미 담당하는 영역이다. 전역 상태는 세션 하나로 제한한다.

### C.3 백엔드 오류 원문을 그대로 표시

구현이 가장 단순하다. **기각** — `REQ-ERR-006`이 금지한다. F2/F3 기본 바디에는 내부 경로(`path`)가 포함되며, 예외 메시지가 그대로 노출될 수 있다.

### C.4 취소 화면을 `DEP-2` 해소 전에 미리 구현 (식별자만 비워둠)

동작하지 않는 화면을 먼저 만들어 두는 방식. **기각되었고, 이제 논점 자체가 소멸했다** — `DEP-2`가 해소되어(`plan.md` §B.2) 취소 화면은 처음부터 실제 식별자로 구현되고 검증된다. 이 기각 판단을 남겨 두는 이유는, 같은 유혹(미해소 의존성 앞에서 "일단 껍데기만" 만들기)이 후속 SPEC에서 재발할 수 있기 때문이다. 기각 근거는 그대로 유효하다 — **검증할 수 없는 코드가 저장소에 남으면 이후 누군가 이를 "구현됨"으로 오인한다.**

### C.5 취소 성공 시 목록에서 항목을 즉시 제거 (낙관적 갱신)

취소 버튼을 누른 즉시 클라이언트가 보유한 목록에서 해당 항목을 지워 반응성을 높이는 방식. **기각** — 확정 취소는 큐를 경유하므로(`REQ-CNL-001`) 202 시점에 취소가 아직 확정되지 않았다. 항목을 먼저 지우면 §C.1이 기각한 낙관적 UI를 **목록 화면에서 우회**하는 셈이 되고, 폴링 결과가 `CANCELLED`가 아닌 값으로 확정될 때 사라졌던 항목이 되살아나 화면이 자기 자신을 뒤집는다. `REQ-CNL-009`가 조회 API 재호출 결과를 표시하도록 못박는다.

대기명단 취소(8번)는 200 동기 응답이므로 이 위험이 없지만, **두 취소 화면의 동작을 동일하게 유지**하기 위해 같은 규칙을 적용한다 — 사용자가 두 화면에서 서로 다른 반응성을 경험할 이유가 없고, 구현이 갈라지면 이후 혼동의 원인이 된다.
