## §2 시퀀스 할당 순서 ≠ 커밋 순서 — D1의 근본 원인

### 관찰된 사실

PostgreSQL의 시퀀스(`BIGSERIAL`의 뒷단)는 **비트랜잭션적**으로 동작한다. `nextval()`은 INSERT가 실행되는 시점에 값을 반환하며, 그 트랜잭션이 롤백되어도 값은 되돌아가지 않는다(그래서 시퀀스에 구멍이 생긴다).

한편 삽입된 행이 **다른 트랜잭션에 보이는 시점**은 INSERT 시점이 아니라 **커밋 시점**이다 (READ COMMITTED 기준).

이 둘을 합치면:

> **시퀀스 값의 대소 관계는 커밋 순서를 보장하지 않는다.**

### 이것이 만드는 실패 시나리오

```
T_X: BEGIN → INSERT (id=5 할당) → ......[지연].......→ COMMIT
T_Y:              BEGIN → INSERT (id=6 할당) → COMMIT
워커:                                    ↑ 여기서 폴링: id=6은 보이고 id=5는 안 보임
```

워커는 `WHERE state='PENDING' ORDER BY id ASC`로 조회하지만, `id=5`가 **아직 가시화되지 않았으므로 결과 집합에 나타나지 않는다.** 워커는 `id=6`(회원 Y)을 확정하고 마지막 자리를 소진한다. 이후 `id=5`(회원 X)가 보이게 되면 정원이 이미 찼으므로 X는 대기명단으로 밀린다.

**결과: 나중에 접수한 Y가 먼저 접수한 X를 앞질렀다.** 이는 REQ-WRK-003의 "나중에 접수된 요청을 먼저 확정 shall not"을 위반한다.

### 왜 테스트로 잘 잡히지 않는가

경쟁 구간이 **폴링 주기보다 짧기 때문**이다. 폴링 주기가 수백 ms이면 대부분의 접수 트랜잭션은 다음 폴링 전에 커밋을 마친다. 순서 검증 테스트는 거의 매번 통과하면서 **무조건적 금지 요구사항이 확률적으로만 만족되는 상태**를 감춘다. 최초 설계가 이 결함을 안고도 "검증됨"으로 보였던 이유가 이것이다.

### 조사에서 검토한 완화책 3가지

| 안 | 방법 | 판단 |
|---|---|---|
| (A) 정의 변경 | "접수 순서"를 `id` 순서로 **정의**하고, 실제 도착 순서와 어긋날 수 있음을 잔여 위험으로 기록 | **기각** — 요구사항을 실패에 맞춰 약화시키는 것. 사용자 가치("먼저 신청한 사람이 먼저")가 훼손된다 |
| (B) 가시성 워터마크 | 진행 중 트랜잭션의 최소 스냅샷 값(`pg_snapshot_xmin(pg_current_snapshot())`) 미만의 행만 처리 | **기각** — 정확하지만, 장수명 트랜잭션 하나가 전체 큐 처리를 무기한 지연시킨다. 지연 목표(REQ-STS-003)와 직접 충돌하고 디버깅이 어렵다 |
| (C) 접수 구간 직렬화 | 순서값 할당 **이전에** 강좌 단위 배타 잠금을 잡고 커밋 시 해제 | **채택** — §4 |

## §3 `FOR UPDATE SKIP LOCKED`의 가시성 의미론

### 핵심 구별

`SKIP LOCKED`는 **"다른 트랜잭션이 행 잠금을 보유 중인 행"을 건너뛴다.** 이것은 **커밋되지 않아 아예 보이지 않는 행**과 전혀 다른 상황이다.

| 상황 | 조회 결과에 포함? | `SKIP LOCKED`가 도움이 되는가 |
|---|---|---|
| 다른 트랜잭션이 UPDATE 잠금 보유 중인 **커밋된** 행 | 후보로 나타남 → 건너뜀 | **예** — 이것이 `SKIP LOCKED`의 용도 |
| 아직 커밋되지 않은 INSERT 행 | **애초에 나타나지 않음** | **아니오** — 건너뛸 대상 자체가 없다 |

§2의 실패 시나리오는 두 번째 줄에 해당한다. **따라서 `SKIP LOCKED`는 D1을 해결하지 못한다.** 최초 설계가 `SKIP LOCKED`를 순서 보장 장치처럼 서술한 것이 오류였다.

`SKIP LOCKED`의 진짜 용도는 **다중 워커가 같은 행을 중복 처리하지 않게 하는 것**이며, 그 목적으로는 정확히 유효하다 (REQ-WRK-013). v1은 워커가 1개이므로 실질적으로 무해하지만, 실수로 인스턴스가 2개 뜨는 사고를 대비해 처음부터 적용해 둔다.

## §4 권고 잠금(advisory lock) — 채택한 해결책

### 메커니즘

접수 트랜잭션이 다음 순서를 지킨다.

```
BEGIN
  SELECT pg_advisory_xact_lock(<course_id 기반 키>);   -- (1) 잠금 먼저
  INSERT INTO enrollment_request (...) ;                -- (2) 그 다음 순서값 할당
COMMIT                                                  -- (3) 커밋 시 잠금 자동 해제
```

`pg_advisory_xact_lock`은 **트랜잭션 범위** 권고 잠금이다. 명시적 해제 호출이 필요 없고, 커밋·롤백 어느 쪽으로 끝나든 자동 해제된다 — 해제 누락으로 인한 교착이 구조적으로 발생하지 않는다.

### 정합성 논증

동일 강좌 `C`에 대한 두 접수 트랜잭션 `T₁`, `T₂`를 생각한다. 잠금이 배타적이므로 두 임계 구간 `[잠금 획득 → 커밋]`은 겹치지 않는다. `T₁`이 먼저 잠금을 얻었다고 하자.

1. `T₁`은 잠금 보유 중에 순서값 `s₁`을 할당하고 커밋하면서 잠금을 놓는다.
2. `T₂`는 그 이후에야 잠금을 얻고 순서값 `s₂`를 할당한다. 시퀀스는 단조 증가하므로 `s₁ < s₂`.
3. 따라서 `s₁ < s₂` **이면서** `commit(T₁) < 잠금획득(T₂) < commit(T₂)`.

일반화하면 강좌 `C`의 모든 큐 행에 대해 **순서값 순서 = 커밋 순서**다. 그 결과:

> 어떤 시점에 워커에게 `C`의 순서값 `s`인 행이 보인다면, `C`의 순서값이 `s`보다 작은 모든 행도 **반드시 이미 보인다.** 즉 워커가 보는 집합은 항상 접수 순서의 **접두사(prefix)** 다.

이것이 REQ-QUE-004 / INV-ENR-007의 근거이며, D1을 **정의 변경 없이** 닫는다.

### 성질과 비용

| 항목 | 평가 |
|---|---|
| 잠금 범위 | **강좌 단위** — 서로 다른 강좌의 접수는 완전히 병렬 |
| 임계 구간 길이 | INSERT 1건 (인덱스 갱신 포함). 밀리초 미만 |
| 처리량 상한 | 단일 강좌 기준 초당 수천 건 규모로 추정 — §6에서 실측 필요 |
| 교착 위험 | 강좌당 잠금 1개만 획득하고 다른 잠금을 중첩 획득하지 않으므로 순환 대기가 성립하지 않음 |
| 워커 영향 | 없음 — 워커는 이 잠금을 획득하지 않는다 |

### 사용자가 배제한 대안과의 구별 (중요)

사용자는 "강좌 행에 대한 직접적 비관적/낙관적 락 방식의 **정원 관리**"를 명시적으로 배제했다. 이 접수 잠금은 그것과 다르다.

| 구분 | 배제된 방식 | 이 SPEC의 접수 잠금 |
|---|---|---|
| 잠그는 대상 | `course` 행 자체 | 강좌 식별자 기반 권고 잠금 키 (행을 잠그지 않음) |
| 목적 | **정원 검사·확정**을 직렬화 | **접수 순서 확정**만 직렬화 |
| 정원 검사 위치 | 잠금 안에서 즉시 확정 | 여전히 **워커**가 수행 (큐 아키텍처 유지) |
| 아키텍처 | 큐 불필요 | DB 테이블 큐 + 워커 (사용자가 선택한 구조 그대로) |

즉 사용자가 선택한 "DB 테이블 큐 + 워커" 아키텍처는 그대로 유지되고, 그 앞단에 **접수 번호표 발급기**를 하나 추가한 것이다.

### 대안: 권고 잠금 대신 `course` 행 `SELECT ... FOR UPDATE`

동일한 직렬화 효과를 얻을 수 있지만, `course` 행 잠금은 강좌 정보 수정 등 다른 경로와 경합하고, 배제된 대안과의 경계가 흐려진다. 권고 잠금은 **접수 순서 전용 키**이므로 의도가 코드에 드러난다. 권고 잠금을 채택한다.

## §5 `@Scheduled` + `@Transactional` 상호작용

조사에서 확인이 필요했던 함정들:

| 함정 | 내용 | 이 SPEC의 대응 |
|---|---|---|
| **자기 호출(self-invocation)** | 같은 빈 내부에서 `this.method()`로 호출하면 프록시를 거치지 않아 `@Transactional`이 **적용되지 않는다** | 워커 클래스(`@Scheduled` 보유)와 요청 1건 처리 클래스(`@Transactional` 보유)를 **분리한다**. 폴링 루프가 별도 빈의 메서드를 호출하게 한다 |
| **배치 전체를 한 트랜잭션으로 묶기** | 배치 중 1건이 실패하면 전체 롤백 → REQ-WRK-009/INV-ENR-005 위반 | **요청 1건 = 트랜잭션 1개** (REQ-WRK-010). 폴링 루프 자체는 트랜잭션 밖 |
| **`fixedRate` vs `fixedDelay`** | `fixedRate`는 이전 실행 완료를 기다리지 않아 겹쳐 실행될 수 있다 | **`fixedDelay` 사용** — 이전 배치 종료 후 지정 시간 대기. 단일 워커 전제(REQ-WRK-012)와 정합 |
| **스케줄러 스레드 풀 크기 기본값 1** | 기본값이 1이라 다른 스케줄 작업과 서로 막을 수 있다 | v1에는 다른 스케줄 작업이 없다. 기본값 유지가 오히려 단일 워커 전제를 강화한다 |
| **테스트에서 스케줄러가 자동 동작** | 통합 테스트에서 예측 불가능한 타이밍 유발 | 테스트 프로파일에서 `@Scheduled` 자동 실행을 **끄고**, 테스트가 워커 처리 메서드를 명시적으로 호출한다. 타이밍 의존 테스트를 제거한다 |
| **예외 처리 위치** | 처리 메서드에서 예외가 새어 나가면 상태 전이(`FAILED` 기록)까지 롤백된다 | `FAILED` 기록은 **별도 트랜잭션**(`REQUIRES_NEW`)으로 수행한다. 도메인 변경은 롤백되고 상태 기록은 남아야 한다 |

마지막 항목은 특히 주의가 필요하다. "요청만 `FAILED`로 종결하고 큐는 계속"(REQ-WRK-009)을 순진하게 구현하면, 같은 트랜잭션에서 `FAILED`를 기록하려다 도메인 변경과 함께 롤백되어 요청이 `PENDING`으로 남고 **무한 재시도 루프**가 된다.

## §6 Testcontainers 기반 동시성 통합 테스트 방법론

### H2 대체가 불가능한 이유 (협상 대상 아님)

| 기능 | PostgreSQL | H2 |
|---|---|---|
| `pg_advisory_xact_lock` | 지원 | **미지원** — §4의 메커니즘 자체를 재현 불가 |
| `FOR UPDATE SKIP LOCKED` | 지원 | 방언·버전에 따라 다르게 동작 |
| 부분 유니크 인덱스 (`WHERE`) | 지원 | 지원 형태가 다름 |
| CHECK 제약 위반 예외 유형 | PostgreSQL 고유 | 다름 |
| 스냅샷 격리 동작 | 실제 MVCC | 근사 |

이 SPEC의 **핵심 검증 대상 전부**가 위 표에 걸린다. H2로 대체하면 테스트는 초록색이 되지만 검증한 것이 없다. plan.md §D에 제약으로 명시한다.

### 동시성 테스트 작성 원칙

1. **실제 스레드로 동시 도달을 만든다.** 단일 스레드 반복문은 경쟁 조건을 재현하지 못한다. `ExecutorService` + `CountDownLatch`로 N개 스레드를 동시에 출발시킨다.
2. **워커를 명시적으로 구동한다.** 스케줄러 자동 실행에 의존하면 테스트가 타이밍에 종속된다. 접수를 모두 끝낸 뒤 워커 처리 루프를 큐가 빌 때까지 호출한다.
3. **커밋 지연을 인위적으로 주입해 순서 보장을 검증한다.** 이것이 §2 결함을 실제로 잡는 유일한 방법이다 — 일부 접수 트랜잭션의 커밋을 지연시킨 상태에서 워커를 돌려, 순서가 여전히 지켜지는지 확인한다.
4. **접수 잠금을 제거한 대조군 테스트를 둔다.** 잠금을 끈 구성에서 3번 시나리오가 **실패**해야 한다. 실패하지 않는다면 테스트가 결함을 재현하지 못하고 있다는 뜻이며, 통과했다는 사실이 아무것도 증명하지 못한다. (spec.md §E 성공 기준 3번)
5. **부하 측정은 별도 테스트로 분리한다.** 지연 목표(REQ-STS-003) 검증은 실행 시간이 길고 환경 편차가 크므로 정합성 테스트와 섞지 않는다.

### 커밋 지연 주입 방법 (run 단계에서 택일)

- 접수 서비스에 테스트 전용 훅(지연 주입 지점)을 두고 테스트 프로파일에서만 활성화
- 또는 테스트가 직접 JDBC 커넥션 2개로 트랜잭션을 수동 제어하여 커밋 순서를 뒤집는다

두 번째가 프로덕션 코드를 오염시키지 않으므로 선호된다. 다만 접수 API 전체 경로를 거치지 않으므로, 두 방법을 조합해 (a) 저수준 순서 보장은 수동 트랜잭션 테스트로, (b) 종단 간 동작은 부하 테스트로 검증한다.

## §7 run 단계에서 실제 확인해야 할 항목 (검증 부채)

아래는 이 문서가 **가설로 기록한** 사항이다. run 단계 M1에서 실제 PostgreSQL로 확인하고 결과를 progress.md §E.2에 기록한다.

| # | 확인 항목 | 확인 방법 |
|---|---|---|
| V1 | `pg_advisory_xact_lock`이 커밋/롤백 시 자동 해제된다 | 트랜잭션 2개로 잠금 경합 시나리오 실행 |
| V2 | 잠금 없이 커밋 순서를 뒤집으면 순서 보장이 **깨진다** | §6-4 대조군 테스트 |
| V3 | 잠금이 있으면 같은 시나리오에서 순서가 **지켜진다** | §6-3 테스트 |
| V4 | 미커밋 INSERT 행이 다른 트랜잭션의 `SELECT ... SKIP LOCKED`에 나타나지 않는다 | 수동 트랜잭션 2개 |
| V5 | 단일 강좌 접수 처리량 실측치 | 부하 테스트에서 초당 접수 건수 측정 |
| V6 | 워커 처리량 실측치 (배치 크기 × 주기 대비) | 부하 테스트에서 큐 소진 시간 측정 → REQ-STS-003 상한 재확인 |
| V7 | `@Scheduled` 자동 실행 비활성화가 테스트 프로파일에서 동작한다 | 테스트 기동 시 워커 미실행 확인 |
| **V8** | **커밋 중 행 가시화가 권고 잠금 해제보다 먼저 일어난다** | V1과 동일한 2-커넥션 하네스: T₁이 잠금을 잡고 INSERT 후 커밋 → T₂가 잠금 획득 즉시 SELECT → **T₁의 행이 보여야 한다.** 반복 실행하여 역전이 관측되지 않음을 확인 |

**V8이 필요한 이유 (2차 감사 E5)**: §4의 정합성 논증은 `commit(T₁) < 잠금획득(T₂) < commit(T₂)`까지를 도출한다. 워커가 **가시적 접두사**를 보장받으려면 여기에 한 가지 성질이 더 필요하다 — PostgreSQL이 커밋 중 **행을 가시화한 뒤에** 그 트랜잭션의 권고 잠금을 해제해야 한다는 것. 문서화된 커밋 경로상으로는 성립하지만(`ProcArrayEndTransaction`이 잠금 해제보다 앞선다), 이 SPEC은 그 의존성을 어디에도 명시하지 않았고 V1은 "커밋/롤백 시 자동 해제" 여부만 확인할 뿐 **해제와 가시화의 순서**는 확인하지 않는다. D1이 정확히 이런 종류의 미검토 엔진 가정에서 비롯되었으므로, 논증의 마지막 고리를 실측으로 닫는다. V1의 하네스를 그대로 재사용하므로 추가 비용은 거의 없다.

**V5·V6의 결과가 REQ-STS-003의 500건 상한과 어긋나면, 요구사항의 숫자를 실측에 맞게 개정한다** — 측정값을 요구사항에 맞추는 것이 아니라 그 반대다.

**V8이 실패하면 §4의 정합성 논증 자체가 성립하지 않는다** — 접수 잠금만으로는 워커의 가시적 접두사가 보장되지 않으므로, 순서 보장 메커니즘을 재설계해야 한다 (SPEC 개정 사유).
