**개정 사유 (rationale)**

후속 `SPEC-FRONTEND-001`의 run 단계에서 브라우저로 실제 흐름을 확인하던 중, `POST /api/courses/{courseId}/enrollments`로 접수한 요청이 워커에 의해 **재현율 100%**(백엔드 3회 이상 재기동에 걸쳐 5회 이상 시도)로 `result='FAILED'`로 종결되는 현상이 관측되었다. 그런데 애플리케이션 로그에 남은 것은 다음 두 줄뿐이었다.

```
큐 요청 처리 시작 requestId=N requestType=ENROLL
큐 요청 처리 종료 requestId=N result=FAILED
```

**예외 스택 트레이스도, 예외 타입도, 예외 메시지도 어디에도 없다.** 원인은 §A.7이 인용한 `EnrollmentQueueWorker.drainQueue()`의 `catch` 블록이 포착한 예외 참조를 **한 번도 사용하지 않고 버리는** 데 있다. 그 결과 이 SPEC이 REQ-WRK-009로 의도적으로 설계한 "1건 실패를 격리하고 큐를 계속 돌린다"는 **생존성 보장이, 실패 원인을 영구히 은폐하는 부작용을 함께 가지고 있었다.**

이것은 관측된 특정 실패와 **독립적인 결함**이다. 근본 원인이 무엇으로 밝혀지든, `FAILED`로 종결된 요청의 원인을 로그로 규명할 수 없다는 사실 자체가 REQ-NFR-004(추적성)의 취지를 절반만 충족한 상태다 — 처리의 **시작·종료·결과**는 기록되지만 **실패의 이유**는 기록되지 않는다. 결함의 소유자가 이 SPEC이므로 이 SPEC이 제자리 개정으로 닫는다.

**이 개정이 규정하지 않는 것 — 근본 원인의 수정 내용**

`processOne`이 왜 예외를 던지는지는 **현재 알려져 있지 않다.** 후보는 (a) 최근 변경으로 유입·노출된 `ENROLL` 디스패치 경로의 로직/데이터 결함, (b) 원격 Supabase 세션 풀러(`aws-0-ap-southeast-1.pooler.supabase.com`)를 쓰는 로컬 개발 환경 고유의 네트워크/커넥션 요인, (c) 그 밖의 것 등이며, **어느 쪽인지는 실제 스택 트레이스를 보기 전에는 결정할 수 없다.** 따라서 이 개정은 요구사항으로 **관측 가능성(REQ-DIAG-001~003)과 그 관측 결과의 기록 의무(REQ-DIAG-004)만** 규정하고, **수정 내용은 규정하지 않는다.** 조사와 그 결과에 따른 조치는 M8의 산출물이며 plan.md §F M8 / progress.md에 기록된다. 조사 결과 애플리케이션 결함으로 판명되어 수정이 이루어지면 그 사실은 후속 소규모 개정으로 spec.md에 반영한다.

> **추측으로 고치지 않는다**는 것이 이 개정의 핵심 판단이다. 원인을 모르는 상태에서 후보 (a)를 가정하고 코드를 바꾸면, 실제 원인이 (b)일 때 **아무것도 고치지 못한 채 검증된 M1~M7 코드만 흔들게 된다.** 관측 → 판정 → 조치 순서를 요구사항과 마일스톤 구조로 강제한다.

**개정이 건드리지 않는 것**

실패 경로에 로깅을 더하는 것뿐이다. 접수 잠금·순서 보장·확정 경로 단일성·승격 헬퍼·`enrolled_count` 변경 경로·트랜잭션 경계는 한 줄도 바뀌지 않으며, REQ-WRK-009(실패 격리)와 REQ-WRK-010(요청 1건 = 트랜잭션 1개)의 **동작은 그대로 유지된다** — REQ-DIAG-003이 이를 요구사항으로 못박는다.

## §A 개요

### A.1 배경

문화센터 강좌의 **선착순 수강신청**을 처리한다. 이 SPEC이 이 프로젝트의 유일한 고난도 영역이며, **핵심 난제는 정합성**이다 — 인기 강좌의 신청 개시 시각에 다수의 요청이 동시에 도착해도 (1) 강좌 정원을 단 1명도 초과해서는 안 되고, (2) 먼저 접수한 사람이 먼저 확정되어야 한다.

이 두 가지를 확보하기 위해 **DB 테이블 기반 순차 큐(queue)** 방식을 채택한다. 모든 수강신청·취소·정원 증설 요청은 즉시 확정되지 않고 접수 순서대로 큐 테이블에 적재되며, 서버의 단일 워커가 큐를 **한 건씩 순차적으로** 처리하면서 정원을 검사하고 확정한다. 사용자는 신청 직후 요청 식별자를 받고 상태 조회 API를 짧은 주기로 폴링하여 결과를 확인한다.

### A.2 접수 순서 보장 — 이 SPEC이 푸는 진짜 문제

"큐 테이블에 넣고 `id` 순서대로 처리한다"는 것만으로는 **선착순이 보장되지 않는다.** 감사에서 확인된 구체적 실패 시나리오는 다음과 같다.

> 회원 X의 접수 트랜잭션이 `id = 5`를 할당받은 직후 커밋이 지연된다(GC 정지, 커넥션 풀 경합 등). 그 사이 회원 Y의 접수 트랜잭션이 `id = 6`을 할당받고 **먼저 커밋**한다. 워커가 폴링하면 `id = 6`은 보이지만 `id = 5`는 **아직 커밋되지 않아 보이지 않는다** — 잠긴 것이 아니라 **가시화되지 않은** 것이므로 `SKIP LOCKED`로는 해결되지 않는다. 워커는 `id = 6`을 확정하며 마지막 자리를 소진하고, 뒤늦게 커밋된 `id = 5`는 대기명단으로 밀린다. **나중에 접수한 Y가 먼저 접수한 X를 앞질렀다.**

원인은 PostgreSQL 시퀀스가 **INSERT 시점에 비트랜잭션적으로** 할당되는 반면, 행의 가시성은 **커밋 시점**에 결정되어 **순서값 순서 ≠ 커밋 순서**가 될 수 있다는 데 있다.

**해결책**: 접수 트랜잭션이 **순서값을 할당하기 전에 강좌 단위 배타 잠금을 획득**하고, 그 잠금을 **커밋 시점에 해제**한다 (PostgreSQL `pg_advisory_xact_lock(course_id)`). 이렇게 하면 동일 강좌의 두 접수 트랜잭션에서 `[잠금 획득 → 순서값 할당 → 커밋]` 구간이 서로 겹치지 않으므로:

> 순서값이 더 작은 요청은 항상 **먼저 커밋**된다. 따라서 순서값이 더 큰 같은 강좌의 행이 워커에게 보이는데 순서값이 더 작은 행이 보이지 않는 상태는 **발생할 수 없다.** 워커에게 보이는 집합은 언제나 접수 순서의 **접두사(prefix)** 다.

이 잠금은 **강좌 단위**이므로 서로 다른 강좌의 접수는 병렬로 진행되고, 임계 구간은 INSERT 1건이라 매우 짧다. 이 메커니즘은 사용자가 배제한 "강좌 행에 대한 직접적 비관적 락 기반 정원 관리"와 **다르다** — 정원 검사는 여전히 워커가 하고, 이 잠금은 오직 **접수 순서 확정**만을 담당한다. 상세한 정합성 논증과 대안 비교는 plan.md §C.2 및 research.md §2에 있다.

**전제**: 이 보장은 **워커 인스턴스가 1개일 때** 성립한다 (REQ-WRK-012). 이 전제는 계획 문서가 아니라 **요구사항으로** 명시한다.

### A.3 용어 정의

| 용어 | 영문 식별자 | 의미 |
|---|---|---|
| 신청 요청 | `EnrollmentRequest` | 큐 테이블에 접수 순서대로 적재되는 1건의 작업 레코드. **아직 확정된 수강신청이 아니다** |

| 대기명단 항목 | `WaitlistEntry` | 정원 초과 시 대기 순번과 함께 등록되는 레코드 |
| 큐 워커 | `EnrollmentQueueWorker` | 큐 테이블을 순차 처리하는 서버 사이드 스케줄러 컴포넌트 |
| 확정 경로 | — | `Enrollment` 생성과 `course.enrolled_count` 변경이 일어나는 **유일한** 코드 경로. v1에서는 워커 1개소 |
| 접수 잠금 | — | 접수 트랜잭션이 순서값 할당 전에 획득하는 강좌 단위 배타 잠금 (§A.2) |

### A.4 상태 도메인 (state machine) — 규범적 정의

이 절은 이 SPEC이 만드는 세 테이블(`enrollment_request`·`enrollment`·`waitlist_entry`)의 상태 값 집합과 합법 전이를 **규범적으로** 확정한다. 아래 표에 없는 값은 저장될 수 없고, 아래에 없는 전이는 수행될 수 없다.

#### A.4.1 큐 상태 도메인 (`enrollment_request`)

큐 행은 **처리 상태**(`state`)와 **처리 결과**(`result`) 두 컬럼을 갖는다. 아래가 두 값 집합의 **완전한 열거**이며, 여기 없는 값은 저장될 수 없다.

**요청 종류 `request_type` (3종)**

| 값 | 적재 주체 | 의미 |
|---|---|---|
| `ENROLL` | 회원 (접수 API) | 수강신청 |
| `CANCEL` | 회원 (취소 API) | 확정 수강신청 취소 + 즉시 승격 |
| `CAPACITY_INCREASE` | 관리자 API | 정원 증설에 따른 대기자 일괄 승격 |

**처리 상태 `state` (2종)**

| 값 | 의미 | 종단 |
|---|---|---|
| `PENDING` | 큐에 접수되었고 아직 처리되지 않음 | 아니오 |
| `DONE` | 워커가 처리를 마쳤음 | **예** |

> **`PROCESSING` 상태를 두지 않는다.** 워커는 요청 1건을 1개 트랜잭션으로 처리하며(REQ-WRK-010), 처리 중인 행은 그 트랜잭션의 **행 잠금**으로 표시된다. 별도의 영속 상태를 두지 않으므로 애플리케이션이 처리 도중 죽어도 트랜잭션이 롤백되어 행은 자동으로 `PENDING`으로 돌아간다 — **멈춘 `PROCESSING` 행이라는 상태 자체가 존재하지 않으며, 복구 스위퍼도 필요 없다.** 이는 단순화이자 장애 복구 설계다.

**처리 결과 `result`** — `state='PENDING'`이면 `NULL`, `state='DONE'`이면 아래 값 중 정확히 하나

| `request_type` | 가능한 `result` 값 | 의미 |
|---|---|---|
| `ENROLL` | `SUCCESS` | 정원 내 확정 |
| | `WAITLISTED` | 정원 초과 → 대기명단 등록 |
| | `CLOSED` | 강좌가 모집 마감되어 처리 불가 |
| | `REJECTED` | 중복 신청 등 요청 자체가 유효하지 않음 |
| | `FAILED` | 처리 중 예기치 못한 오류 |
| `CANCEL` | `CANCELLED` | 취소 완료. 강좌가 `OPEN`이고 활성 대기자가 있으면 대기자 1명 승격 포함, 강좌가 `CLOSED`이면 **취소만 수행하고 승격 없음** (REQ-WL-011) |
| | `REJECTED` | 소유자 불일치 / 이미 취소됨 / 대상 없음 |
| | `FAILED` | 처리 중 예기치 못한 오류 |
| `CAPACITY_INCREASE` | `PROMOTED` | 1명 이상 승격 완료 |
| | `NOOP` | 승격 대상 활성 대기자 없음 |
| | `CLOSED` | 강좌가 모집 마감되어 승격을 수행하지 않음 (REQ-ADX-005) |
| | `FAILED` | 처리 중 예기치 못한 오류 |

**합법 전이 (이 2개가 전부)**

```
(신규 적재)  →  state=PENDING, result=NULL
PENDING      →  state=DONE,    result=<위 표의 값 중 1개>   [워커 처리, 1회만]
```

`DONE → PENDING` 전이는 존재하지 않는다. `result`는 `DONE` 전이 시 정확히 1회 설정되고 이후 변경되지 않는다 (INV-ENR-006).

**클라이언트 노출 상태** = `state='PENDING'`이면 `PENDING`, 아니면 `result` 값을 그대로 노출한다.

#### A.4.2 확정 수강신청 상태 도메인 (`enrollment.status`, 2종)

| 값 | 의미 | 종단 |
|---|---|---|
| `ENROLLED` | 유효한 확정 수강신청. `enrolled_count` 계산의 대상이며 `(member_id, course_id) WHERE status='ENROLLED'` 부분 유니크 인덱스의 대상이다 | 아니오 |
| `CANCELLED` | 취소됨. 이력으로 보존되고 `enrolled_count` 계산에서 제외되며 부분 유니크 인덱스의 대상이 아니다 | **예** |

**합법 전이 (이 2개가 전부)**

```
(신규 생성)  →  status=ENROLLED
ENROLLED     →  status=CANCELLED           [워커의 CANCEL 처리, 1회만]
```

`CANCELLED → ENROLLED` 역전이는 존재하지 않는다. 취소 후 같은 강좌에 재신청하면 **새 `ENROLLED` 행**이 생성된다 (REQ-WRK-007의 중복 검사는 `ENROLLED` 행만 본다 — AC-ENR-040).

"유효한 확정 수강신청"이라는 표현은 이 SPEC 전체에서 `status='ENROLLED'`인 행만을 가리킨다.

#### A.4.3 대기명단 항목 상태 도메인 (`waitlist_entry.status`, 4종)

| 값 | 의미 | 종단 |
|---|---|---|
| `WAITING` | 활성 대기. 순번을 점유하고 승격 대상이며, 부분 유니크 인덱스 2종(`(course_id, position)`·`(member_id, course_id)`, 둘 다 `WHERE status='WAITING'`)의 대상이다 | 아니오 |
| `PROMOTED` | 승격되어 확정 수강신청이 생성됨 (REQ-WL-003, REQ-ADX-002) | **예** |
| `CANCELLED` | 대기자 본인이 자신의 대기를 취소함 (REQ-WL-007) | **예** |
| `DUPLICATE` | 승격 시점에 해당 강좌에 이미 유효한 확정을 보유하여 **승격 부적격**으로 판정되어 건너뛰어진 항목 (REQ-WL-009). REQ-WL-009가 말하는 "중복 상태로 종결"이 가리키는 값이 이것이다 | **예** |

**합법 전이 (이 4개가 전부)**

```
(신규 생성)  →  status=WAITING
WAITING      →  status=PROMOTED            [승격]
WAITING      →  status=CANCELLED           [대기자 본인의 대기 취소]
WAITING      →  status=DUPLICATE           [승격 부적격 판정 후 종결]
```

종단 3종(`PROMOTED`·`CANCELLED`·`DUPLICATE`)에서 나가는 전이는 존재하지 않는다.

**"활성(active)"의 규범적 정의**: 이 SPEC 전체에서 "활성 대기자 / 활성 대기명단 항목 / 활성 대기 순번"은 모두 `status='WAITING'`인 항목만을 가리킨다. 종단 3종은 순번을 점유하지 않고 부분 유니크 인덱스의 대상도 아니므로, 대기를 취소했거나 승격이 끝난 회원의 재신청을 막지 않는다. 다만 **순번 값 자체는 재사용되지 않는다** — 부여 규칙은 REQ-WL-001에 있다.

### A.5 마감(`CLOSED`) 강좌에서의 요청 처리 정책 — 규범적 결정

`SPEC-COURSE-001`은 강좌 **삭제를 물리 삭제가 아닌 `CLOSED` 전이로** 처리한다 (REQ-ADM-008). 따라서 관리자가 "삭제"한 강좌에도 확정자와 대기자가 그대로 남아 있을 수 있고, 그 상태에서 `CANCEL`·`CAPACITY_INCREASE`가 처리될 수 있다. 이 조합에서 무엇을 해야 하는지 정하지 않으면 구현자가 임의로 결정하게 되므로, 여기서 **명시적으로 확정한다.**

| 요청 | 강좌가 `CLOSED`일 때의 동작 | 결과값 |
|---|---|---|
| `ENROLL` | 확정도 대기 등록도 하지 않음 (기존 REQ-WRK-006) | `CLOSED` |
| `CANCEL` | **취소는 정상 수행** — 확정 레코드를 취소 상태로 전이하고 `enrolled_count`를 1 감소시킨다. **승격은 수행하지 않는다** (REQ-WL-011) | `CANCELLED` |
| `CAPACITY_INCREASE` | 어떤 대기자도 승격하지 않는다 (REQ-ADX-005) | `CLOSED` |

**채택 근거 — "취소는 허용, 승격은 동결"**:

1. **승격 동결이 `CLOSED`의 의미와 일치한다.** `CLOSED`는 "신규 확정 수강신청을 받지 않는다"는 뜻이고, REQ-WRK-006이 `ENROLL`에 대해 이미 그렇게 정의했다. 대기자 승격도 **새로운 확정 수강신청을 만드는 행위**이므로 같은 규칙을 받아야 한다. 승격을 허용하면 관리자가 삭제했다고 믿는 강좌에 새 확정자가 계속 생겨나며, 이는 `SPEC-COURSE-001` REQ-ADM-008의 삭제 의미를 무너뜨린다.
2. **취소 차단은 회원을 가둔다.** 반대로 `CLOSED`를 이유로 취소까지 막으면, 관리자가 마감한 순간 확정자는 자기 수강신청에서 빠져나올 방법이 없어진다. 취소는 회원 본인의 권리이며 새 확정을 만들지 않으므로 `CLOSED`의 취지에 저촉되지 않는다.
3. 기각한 대안 — **"기존 대기명단은 존중하여 승격한다"**: 마감된(=삭제된) 강좌에 확정자가 새로 생기는 것을 관리자가 관측할 수 없고, 대기자 입장에서도 이미 사라진 강좌에 배정되는 것이 이득이 아니다. 대기자 구제가 필요하면 관리자가 강좌를 다시 `OPEN`으로 되돌린 뒤 정원 증설을 요청하는 경로가 있다.

대기명단 항목 자체는 이 정책에서 **삭제하거나 취소 처리하지 않는다** — 강좌가 다시 `OPEN`이 될 수 있으므로 순번을 보존한다. 대기자는 언제든 자신의 대기를 직접 취소할 수 있다 (REQ-WL-007).

| GET | `/api/enrollments/mine` | 요청자 본인의 **활성 확정 수강신청**(`status='ENROLLED'`) 목록 |
| GET | `/api/waitlist-entries/mine` | 요청자 본인의 **활성 대기명단 항목**(`status='WAITING'`) 목록 |

**경로 접두사를 취소 경로와 일치시킨 이유**: 클라이언트의 사용 흐름이 `GET /api/enrollments/mine` → `enrollmentId` 획득 → `DELETE /api/enrollments/{enrollmentId}`이므로, 같은 리소스 접두사를 쓰면 조회와 취소의 대응이 경로만 보고 드러난다. 새 최상위 접두사(`/api/me/...`)를 도입하지 않는 편은 부수 효과도 없다 — 두 경로 모두 `SecurityConfig`의 어떤 `permitAll` 매처에도 걸리지 않아 기존 `anyRequest().authenticated()` 기본 규칙이 그대로 적용되며, **인가 규칙을 추가할 필요가 없다** (`SecurityConfig`는 이 SPEC의 PRESERVE 대상이다).

**기각한 대안 — `EnrollmentStatusResponse`에 식별자 2개를 추가**: 변경량은 더 작지만, 그렇게 하면 **요청 식별자를 보관하고 있는 클라이언트만** 취소할 수 있다. 새 탭을 연 사용자·다른 기기에서 접속한 사용자는 여전히 취소 경로가 없으므로 계약 공백이 절반만 닫힌다. 목록 조회 방식은 보관 상태와 무관하게 완결적이다.

#### A.6.2 응답 계약 (규범적)

두 응답 모두 **배열**이며, 대상이 없으면 빈 배열과 200을 반환한다 (404가 아니다 — "내 목록이 비어 있음"은 정상 상태다).

| 엔드포인트 | 항목 필드 | 정렬 |
|---|---|---|
| `GET /api/enrollments/mine` | `enrollmentId`, `courseId`, `courseTitle`, `status`, `enrolledAt` | `enrollmentId` 오름차순 |
| `GET /api/waitlist-entries/mine` | `waitlistEntryId`, `courseId`, `courseTitle`, `position`, `status` | `position` 오름차순 |

- `enrollmentId` / `waitlistEntryId`는 **각각 `DELETE /api/enrollments/{enrollmentId}` / `DELETE /api/waitlist-entries/{entryId}`가 받는 값과 동일한 식별자**여야 한다. 이 동일성이 개정의 목적 그 자체이므로 요구사항(REQ-LST-006)과 인수 기준(AC-ENR-056)으로 명시한다.
- `courseTitle`은 취소 버튼 옆에 "무엇을 취소하는지"를 표시하기 위한 값이다. 강좌 식별자만 반환하면 클라이언트가 강좌 조회를 N회 더 호출해야 한다.
- `status`는 §A.4.2 / §A.4.3의 상태값을 그대로 노출한다. 현재 반환 범위가 활성 1종뿐이어서 값이 고정되지만, 클라이언트가 상태를 추론으로 가정하지 않게 하고 향후 이력 노출로 확장할 때 응답 형태가 바뀌지 않도록 포함한다.
- 정렬을 규범으로 못박는 이유는 **인수 기준이 관찰 가능해야 하기 때문**이다. 정렬이 미정이면 AC가 순서를 단언할 수 없다.

#### A.6.3 반환 범위를 "활성"으로 한정하는 이유

두 엔드포인트는 §A.4의 **활성 상태만** 반환한다 — 확정은 `ENROLLED`, 대기는 `WAITING`. 종단 상태(`CANCELLED`·`PROMOTED`·`DUPLICATE`)는 반환하지 않는다.

1. **목적 적합성**: 이 엔드포인트의 존재 이유는 취소 대상 지목이며, 취소 가능한 것은 활성 항목뿐이다. 종단 항목의 식별자를 받아도 취소는 `REJECTED`된다 (REQ-CNL-005).
2. **최소 노출**: 이력 조회는 별개의 기능이며 이 개정의 범위가 아니다 (§D 범위 제외).

#### A.6.4 소유권 범위 한정 — 구조에 의한 안전

두 엔드포인트는 **회원 식별자를 입력으로 받지 않는다.** 반환 집합은 오직 인증 주체(`Authentication`)에서 유도한 회원 식별자로 결정되며, 다른 회원의 데이터를 지목할 수 있는 경로 변수·쿼리 파라미터·요청 본문 필드가 **존재하지 않는다.** 이는 `GET /api/enrollment-requests/{requestId}`(REQ-STS-002)가 식별자를 받은 뒤 소유권을 **검사**하여 막는 것과 다르며, 애초에 조작할 입력이 없으므로 **구조적으로 안전하다** (INV-ENR-010).

이 성질은 `DEP-2` 조사가 "사용자에게 식별자를 직접 입력받기" 우회안을 기각한 이유와 정확히 맞물린다 — 그 우회안은 화면을 열거 시도 표면으로 만들지만, 목록 조회는 열거할 대상 자체를 없앤다.

### A.7 큐 처리 실패의 진단 불가능성 — v0.3.1 개정

이 절은 v0.3.1 제자리 개정으로 신설되었다. 배경과 발견 경위는 위 `## Amendments` § 개정 2에 있다.

#### A.7.1 확인된 결함 — 포착된 예외의 무기록 폐기

**직접 확인한 현재 코드**다. `src/main/java/com/hongseob/openclass_ap/enrollment/worker/EnrollmentQueueWorker.java` **60~74행** `drainQueue()`의 내부 루프, **65~69행**:

```java
65                try {
66                    processor.processOne(id);
67                } catch (RuntimeException ex) {
68                    processor.recordFailure(id);
69                }
```

포착한 예외 참조 `ex`는 **67행에서 선언된 뒤 어디에서도 사용되지 않는다.** 68행의 `recordFailure(id)`는 예외를 인자로 받지 않으며, 그 구현(`EnrollmentRequestProcessor` 115~123행)도 `state='DONE'`·`result='FAILED'` 기록과 `"큐 요청 처리 종료 requestId={} result={}"` 한 줄만 남긴다 — **예외 타입도, 메시지도, 스택 트레이스도 기록하지 않는다.** 즉 `ex`는 catch 블록 종료와 함께 소멸한다.

#### A.7.2 그 결과 로그가 보여주는 것과 감추는 것

이 구조 때문에, `ENROLL` 요청이 실패했을 때 로그에 남는 것은 정확히 다음 두 줄이다.

| 줄 | 출처 | 남는 정보 |
|---|---|---|
| `큐 요청 처리 시작 requestId=N requestType=ENROLL` | `EnrollmentRequestProcessor.processOne` 99행 | 처리를 시작했다 |
| `큐 요청 처리 종료 requestId=N result=FAILED` | `EnrollmentRequestProcessor.recordFailure` 121행 | 실패로 종결했다 |

`processOne`의 정상 종료 로그(102행)는 `dispatch`가 예외를 던지면 **도달하지 않으며**, 트랜잭션이 롤백된 뒤 별도 트랜잭션의 `recordFailure`가 두 번째 줄을 남긴다. 두 줄 사이에 있었던 예외는 **어떤 흔적도 남기지 않는다.**

따라서 `result='FAILED'`인 요청에 대해 운영자·구현자가 로그에서 알 수 있는 것은 **"실패했다"뿐이며, "왜 실패했는가"는 알 수 없다.** 원인 규명에는 디버거 부착이나 코드 수정 후 재현이 필요하고, 그 자체가 이 SPEC이 REQ-NFR-004로 확보하려던 추적성의 목적을 무력화한다.

#### A.7.3 이 결함의 독립성

이 결함은 v0.3.1 개정의 계기가 된 특정 실패 현상과 **논리적으로 독립**이다. 그 현상의 근본 원인이 애플리케이션 결함이든 외부 인프라 요인이든, "실패 원인을 로그로 규명할 수 없다"는 성질은 그대로 남는다. 그러므로 이 절이 규정하는 **관측 가능성** 요구사항(§B.9의 REQ-DIAG-001 ~ 003)은 **원인 규명의 결과에 조건부가 아니며**, M8 Step A로 항상 이행된다. §B.9의 REQ-DIAG-004는 그 관측이 이루어진 **뒤의 기록 의무**이므로 M8 Step B에 대응하며, 조사 결과가 (a)든 (b)든 기록 의무 자체는 동일하게 이행된다.

반대 방향의 의존은 성립한다 — **관측 수단 없이는 원인을 판정할 수 없으므로**, 근본 원인 조사(M8 Step B)는 이 요구사항의 이행을 선행 조건으로 갖는다.

## §B 요구사항 (GEARS)

### B.1 접수 및 접수 순서 보존 (QUE)

- **REQ-QUE-001** (Ubiquitous) — 큐 테이블은 각 요청의 접수 순서를 전역 단조 증가 순서값으로 보존 **shall**한다.
- **REQ-QUE-002** (Event-driven) — **When** 인증된 회원의 수강신청 요청이 도착하면, 접수 API는 정원 검사나 확정 처리를 수행하지 않고 요청을 `state='PENDING'`으로 큐에 적재한 뒤 요청 식별자를 즉시 반환 **shall**한다.
- **REQ-QUE-003** (Ubiquitous) — 큐 행을 적재하는 **모든** 트랜잭션(`ENROLL` 접수·`CANCEL` 접수·`CAPACITY_INCREASE` 적재)은 큐 행의 순서값을 할당하기 **이전에** 대상 강좌 단위의 배타 잠금을 획득 **shall**하며, 그 잠금은 트랜잭션 커밋 시점에 해제 **shall**된다. 동일 강좌에 대한 두 적재 트랜잭션의 `[잠금 획득 → 순서값 할당 → 커밋]` 구간은 서로 겹치 **shall not**한다. 잠금을 획득하지 않고 큐 행을 적재하는 프로덕션 경로가 존재 **shall not**한다.

  > **범위가 3종 전부인 이유 (2회차 감사 후속 N2)**: REQ-QUE-004의 가시화 순서 보장은 "동일 강좌의 **큐 행**"에 대한 명제이지 `ENROLL` 행에 국한되지 않는다. 한 종류라도 잠금 없이 적재되면 그 종류의 행에서 순서값 순서 ≠ 커밋 순서가 되어 REQ-QUE-004가 성립하지 않으며, 워커가 보는 집합이 접수 순서의 접두사라는 성질(§A.2)도 깨진다. AC-ENR-005는 이미 "잠금 획득 없이 큐 행을 INSERT하는 프로덕션 경로가 0건"이라는 3종 전부의 조건을 검증하고 있었고, 이 개정은 요구사항 문구를 그 검증 범위에 맞춘 것이다 — 설계 변경이 아니다.
- **REQ-QUE-004** (Ubiquitous) — 동일 강좌에 대해, 큐 행 순서값의 오름차순은 그 행이 다른 트랜잭션에 가시화되는 순서와 일치 **shall**한다. 순서값이 더 큰 행이 가시화되었는데 순서값이 더 작은 같은 강좌의 행이 아직 가시화되지 않은 상태는 존재 **shall not**한다.
- **REQ-QUE-005** (Event-driven) — **When** 존재하지 않는 강좌 식별자로 접수 요청이 감지되면, 접수 API는 404를 반환하고 큐 행을 적재 **shall not**한다.
- **REQ-QUE-006** (State-driven) — **While** 요청자가 인증되지 않은 상태이면, 접수·취소·상태 조회 API는 401을 반환 **shall**하며 큐 행을 적재 **shall not**한다.
- **REQ-QUE-007** (Ubiquitous) — 큐 행은 §A.4에 열거된 `request_type` 값 중 정확히 하나를 보유 **shall**하며, 그 외의 값을 저장 **shall not**한다.

### B.2 큐 워커 (WRK)

- **REQ-WRK-001** (Ubiquitous) — 확정 수강신청(`Enrollment`) 레코드를 생성하는 코드 경로는 큐 워커 처리 경로 **단 1개소** **shall**이다. 컨트롤러·접수 서비스·취소 서비스·관리자 서비스는 물론, JPA 연쇄 저장(cascade)·`merge`·변경 감지(dirty checking)를 포함한 어떤 간접 경로로도 생성 **shall not**된다.
- **REQ-WRK-002** (Ubiquitous) — `course.enrolled_count` 값을 변경하는 코드 경로는 큐 워커 처리 경로 **단 1개소** **shall**이다. 접수 API·취소 API·관리자 API는 이 값을 직접 변경 **shall not**한다.
- **REQ-WRK-003** (Ubiquitous) — 큐 워커는 `state='PENDING'`인 행을 순서값 오름차순으로 처리 **shall**하며, 동일 강좌에 대해 나중에 접수된 요청을 먼저 확정 **shall not**한다.
- **REQ-WRK-004** (State-driven) — **While** 대상 강좌가 모집 중이고 확정 인원이 정원 미만이면, 워커는 `ENROLL` 요청을 확정 처리하고 `enrolled_count`를 1 증가시키며 결과를 `SUCCESS`로 기록 **shall**한다.
- **REQ-WRK-005** (State-driven) — **While** 대상 강좌가 모집 중이고 확정 인원이 정원에 도달했으면, 워커는 확정 처리를 하지 않고 요청자를 대기명단에 등록하며 결과를 `WAITLISTED`로 기록 **shall**한다.
- **REQ-WRK-006** (State-driven) — **While** 대상 강좌의 모집 상태가 `CLOSED`이면, 워커는 `ENROLL` 요청에 대해 확정도 대기 등록도 수행하지 않고 결과를 `CLOSED`로 기록 **shall**한다.
- **REQ-WRK-007** (Event-driven) — **When** 동일 회원이 대상 강좌에 대해 **아래 세 상태 중 하나**에 해당하는데도 `ENROLL` 요청을 시도한 것이 감지되면, 워커는 결과를 `REJECTED`로 기록 **shall**하며 중복 확정 레코드도 중복 대기명단 항목도 생성 **shall not**한다.
  1. 해당 강좌에 **유효한 확정 수강신청**을 이미 보유
  2. 해당 강좌에 대한 **미처리(`PENDING`) 큐 요청**을 이미 보유
  3. 해당 강좌에 **활성 대기명단 항목**(`WAITING`)을 이미 보유

  > 3번은 2차 감사(E1)에서 추가되었다. 1·2번만으로는, 이미 대기자가 된 회원이 조급함에 재신청했을 때(`DONE` 처리된 이전 요청은 2번에 걸리지 않는다) **동일 회원이 같은 강좌의 대기 순번을 2개 점유**하게 된다. 공정성이 훼손될 뿐 아니라, 그중 하나가 먼저 승격되면 남은 항목이 승격 시점에 중복 확정을 시도하여 큐 선두를 영구히 막는다 (REQ-WL-009가 그 2차 방어선이다).
- **REQ-WRK-008** (Ubiquitous) — 데이터베이스는 동일 강좌·동일 회원의 유효한 확정 수강신청이 2건 이상 존재하는 상태를 제약 조건 수준에서 거부 **shall**한다.
- **REQ-WRK-009** (Event-driven) — **When** 워커가 한 요청을 처리하던 중 예외를 감지하면, 워커는 해당 요청만 결과 `FAILED`로 종결하고 큐의 나머지 요청 처리를 계속 **shall**한다. 단일 요청의 실패가 큐 전체를 정지 **shall not**시킨다.
- **REQ-WRK-010** (Ubiquitous) — 워커는 요청 1건을 1개의 트랜잭션으로 처리 **shall**하며, 그 트랜잭션은 상태 전이(`state='DONE'` + `result` 기록)와 도메인 변경(확정 생성·대기 등록·카운터 증감)을 원자적으로 커밋 **shall**한다.
- **REQ-WRK-011** (Ubiquitous) — 워커는 이미 `state='DONE'`인 요청을 재처리 **shall not**한다 (멱등성).
- **REQ-WRK-012** (Ubiquitous) — v1 배포는 큐 워커를 **단 1개 인스턴스만** 구동 **shall**한다. REQ-WRK-003의 순서 보장은 이 전제 위에서 성립하며, 이 전제가 깨지면 순서 보장은 성립 **shall not**한다.
- **REQ-WRK-013** (Capability gate) — **Where** 워커 인스턴스가 2개 이상 동시 구동되는 배치이면, 각 워커는 행 단위 배타 점유(`SELECT ... FOR UPDATE SKIP LOCKED`)를 사용 **shall**하며, 동일 행이 두 워커에서 중복 처리 **shall not**된다. 이 배치에서 REQ-WRK-003의 순서 보장은 성립하지 않으며, 순서 보장이 필요한 다중 인스턴스 운영은 이 SPEC의 범위가 아니다.
- **REQ-WRK-014** (Ubiquitous) — 데이터베이스는 확정 인원이 정원을 초과하는 상태를 제약 조건 수준에서 거부 **shall**한다. 애플리케이션 로직 검사만을 유일한 방어선으로 삼아서는 **shall not** 한다.
- **REQ-WRK-015** (Ubiquitous) — 워커의 처리 주기와 1회 배치 크기는 REQ-STS-003이 정한 부하 상한에서 지연 목표를 달성할 수 있는 값으로 설정 **shall**되며, 그 산출 근거가 문서에 기록 **shall**된다.

### B.3 상태 조회 (STS)

- **REQ-STS-001** (Event-driven) — **When** 인증된 회원이 자신의 요청 식별자로 상태 조회를 요청하면, 상태 조회 API는 §A.4의 클라이언트 노출 상태값 중 하나를 반환 **shall**하고, 대기 상태인 경우 대기 순번을 함께 반환 **shall**한다.
- **REQ-STS-002** (Event-driven) — **When** 다른 회원의 요청 식별자로 상태 조회가 시도된 것이 감지되면, 상태 조회 API는 해당 요청의 내용을 노출 **shall not**하고 403 또는 404를 반환 **shall**한다.
- **REQ-STS-003** (Ubiquitous) — 동일 강좌에 대한 **동시 접수 요청이 500건 이하인 부하**에서, 시스템은 요청 접수 시점부터 종단 결과 확정까지의 지연이 **5초 이내**가 되도록 큐 처리 주기와 배치 크기를 구성 **shall**한다. 이 상한을 초과하는 부하에서는 지연이 큐 깊이에 비례하여 증가 **shall**하며, 그 특성을 API 문서에 명시 **shall**한다.
- **REQ-STS-004** (Ubiquitous) — 상태 조회 API는 부작용 없는 읽기 전용 동작 **shall**이어야 하며, 호출 횟수에 따라 시스템 상태를 변경 **shall not**한다.

### B.4 대기명단 (WL)

- **REQ-WL-001** (Ubiquitous) — 대기명단은 등록 순서에 따른 결정적 순번을 유지 **shall**하며, 동일 강좌 내 활성 대기 순번이 중복 **shall not**된다. 새 대기명단 항목의 순번은 **해당 강좌의 전체 대기명단 이력**(종단 상태 `PROMOTED`·`CANCELLED`·`DUPLICATE` 항목을 포함한다)에서 관측된 **최대 순번 + 1**로 부여 **shall**된다. 현재 활성 항목의 **개수**(`COUNT`)에 기반하여 부여 **shall not**하며, 한 번 부여된 순번 값은 그 항목이 종단 상태가 된 뒤에도 재사용 **shall not**된다.

  > **`COUNT(활성)+1`을 금지하는 이유 (2회차 감사 후속 N5)**: 순번은 활성 항목만 점유하지만(§A.4.3), 승격·취소로 종단이 된 항목의 순번 값은 이력에 남는다. 대기자 C(1)·D(2) 상태에서 C가 승격되면 활성 항목은 D 하나이므로 `COUNT(활성)+1 = 2`가 되어 **D가 이미 쓰고 있는 순번 2와 충돌**한다. 그 INSERT는 `(course_id, position) WHERE status='WAITING'` 부분 유니크 인덱스에 걸려 예외가 되고, 예외가 `processOne` 트랜잭션 **전체를 롤백**시켜 REQ-WL-009가 막으려는 것과 **동일한 큐 선두 정지(생존성 결함)** 를 만든다. `MAX(순번) + 1`은 종단 항목의 순번까지 세므로 이 충돌이 구조적으로 발생하지 않는다. AC-ENR-031의 역순 사례(C 승격 후 E가 순번 3을 받는다)가 암묵적으로 요구하던 규칙을 여기서 규범화한다.
- **REQ-WL-002** (Ubiquitous) — 데이터베이스는 동일 강좌 내 활성 대기 순번의 중복을 제약 조건 수준에서 거부 **shall**한다.
- **REQ-WL-003** (Event-driven) — **When** 워커가 `CANCEL` 요청을 처리하면, 워커는 **같은 트랜잭션 안에서** 확정 레코드를 취소 상태로 전이하고 `enrolled_count`를 1 감소시킨 뒤, **강좌가 모집 중인 동안**(강좌가 `CLOSED`이면 승격을 수행하지 않는다 — REQ-WL-011) 해당 강좌에 **승격 적격인**(REQ-WL-009의 부적격 건너뛰기 대상은 제외한다) 활성 대기자가 존재하면 가장 앞선 순번의 적격 대기자 1명을 즉시 확정으로 승격하고 그 대기명단 항목을 `PROMOTED`로 전이 **shall**한다.
- **REQ-WL-004** (State-driven) — **While** 대상 강좌가 모집 중이면, 취소로 발생한 여유 정원은 승격 적격인 활성 대기자가 존재하는 한 그 대기자에게 우선 배정 **shall**된다. 취소 시점에 그런 대기자가 존재하는데도 그 여유 정원이 대기자보다 늦게 접수된 신규 `ENROLL` 요청에 배정 **shall not**된다.
- **REQ-WL-005** (Event-driven) — **When** 워커가 `CANCEL` 요청을 처리하는 시점에 해당 강좌에 활성 대기자가 없는 것이 감지되면, 워커는 새 확정 레코드를 생성하지 않고 1 감소된 `enrolled_count`를 유지한 채 처리를 정상 종료 **shall**한다.
- **REQ-WL-006** (Ubiquitous) — 승격 처리는 확정 인원이 정원을 초과하지 않는 범위에서만 수행 **shall**된다. 승격 경로는 REQ-WRK-014의 정원 제약을 우회 **shall not**한다.
- **REQ-WL-007** (Event-driven) — **When** 대기자가 자신의 대기 신청 취소를 요청하면, 시스템은 해당 대기명단 항목을 취소 상태로 전이 **shall**하며, 그보다 뒤 순번 대기자들의 상대적 순서를 변경 **shall not**한다.
- **REQ-WL-008** (Event-driven) — **When** 대기 신청 취소 요청이 그 대기명단 항목의 소유자가 아닌 회원으로부터 도착한 것이 감지되면, 시스템은 취소를 수행 **shall not**하고 403 또는 404를 반환 **shall**한다.
- **REQ-WL-009** (Event-driven) — **When** 승격 처리 중 대기 순번이 가장 앞선 대기자가 **승격 부적격**(해당 강좌에 이미 유효한 확정 수강신청을 보유)인 것이 감지되면, 워커는 그 항목을 **건너뛰고 다음 활성 대기자로 진행** **shall**하며, 트랜잭션 전체를 실패시키 **shall not**한다. 건너뛴 항목은 `status='DUPLICATE'`(§A.4.3)로 종결 처리 **shall**되어 다시 대기 선두에 남지 **shall not**한다.

  > 이 요구사항이 없으면 부적격 대기자에 대한 확정 INSERT가 부분 유니크 인덱스에 걸려 예외가 되고, 그 예외가 `processOne` 트랜잭션 전체를 롤백시켜 **취소가 소실되고 여유 정원이 영원히 재배정되지 않는다.** 그 항목은 계속 큐 선두에 남아 이후의 모든 `CANCEL`을 동일하게 실패시킨다 — 생존성(liveness) 결함이다. REQ-WRK-007의 3번 상태가 진입을 막고, 이 요구사항이 이미 만들어진 상태에서 복구를 보장한다.
- **REQ-WL-010** (Ubiquitous) — 데이터베이스는 동일 강좌·동일 회원의 활성 대기명단 항목이 2건 이상 존재하는 상태를 제약 조건 수준에서 거부 **shall**한다. 애플리케이션 검사(REQ-WRK-007)만을 유일한 방어선으로 삼아서는 **shall not** 한다.
- **REQ-WL-011** (State-driven) — **While** 대상 강좌의 모집 상태가 `CLOSED`이면, 워커는 `CANCEL` 요청에 대해 확정 취소와 `enrolled_count` 감소는 정상 수행 **shall**하되 대기자 승격은 수행 **shall not**하며, 결과를 `CANCELLED`로 기록 **shall**한다 (§A.5).

### B.5 확정 취소 (CNL)

- **REQ-CNL-001** (Event-driven) — **When** 인증된 회원이 자신의 확정 수강신청 취소를 요청하면, 취소 API는 확정 레코드와 `enrolled_count`를 직접 변경하지 않고 `CANCEL` 요청을 큐에 적재한 뒤 요청 식별자를 반환 **shall**한다.
- **REQ-CNL-002** (Event-driven) — **When** 확정 수강신청 취소 요청이 그 수강신청의 소유자가 아닌 회원으로부터 도착한 것이 감지되면, 취소 API는 취소를 수행하지 않고 `CANCEL` 요청을 큐에 적재하지 않으며 403 또는 404를 반환 **shall**한다.
- **REQ-CNL-003** (Ubiquitous) — 큐 워커는 `CANCEL` 요청을 처리할 때 요청자와 대상 확정 레코드의 소유자가 일치하는지 **다시** 검증 **shall**하며, 불일치가 감지되면 결과를 `REJECTED`로 기록하고 어떤 도메인 변경도 수행 **shall not**한다.
- **REQ-CNL-004** (Ubiquitous) — v1에서 확정 수강신청의 취소 권한은 **본인에게만** 부여 **shall**된다. 관리자 대리 취소 기능을 제공 **shall not**한다.
- **REQ-CNL-005** (Event-driven) — **When** 이미 취소되었거나 존재하지 않는 확정 수강신청에 대한 `CANCEL` 요청이 처리되면, 워커는 어떤 도메인 변경도 수행하지 않고 결과를 `REJECTED`로 종결 **shall**한다.

### B.6 관리자 연동 확장 (ADX)

`SPEC-COURSE-001`이 정의한 관리자 강좌 API의 동작을 이 SPEC이 확장한다.

- **REQ-ADX-001** (Event-driven) — **When** 관리자가 강좌 정원을 증가시키면, 시스템은 `CAPACITY_INCREASE` 요청을 큐에 적재 **shall**하며, 승격 처리를 관리자 API 경로에서 직접 수행 **shall not**한다.
- **REQ-ADX-002** (Compound) — **While** 대상 강좌가 모집 중이고 **When** 워커가 `CAPACITY_INCREASE` 요청을 처리하면, 워커는 확정 인원이 정원에 도달할 때까지 대기 순번 오름차순으로 **승격 적격인** 대기자를 승격 **shall**하며(부적격 항목은 REQ-WL-009에 따라 건너뛴다), 정원을 초과 **shall not**한다. 강좌가 `CLOSED`이면 어떤 대기자도 승격 **shall not**한다 (REQ-ADX-005).
- **REQ-ADX-003** (Event-driven) — **When** 워커가 `CAPACITY_INCREASE` 요청 처리 시점에 승격 대상 활성 대기자가 없는 것을 감지하면, 어떤 확정 레코드도 생성하지 않고 결과를 `NOOP`으로 기록 **shall**한다.
- **REQ-ADX-004** (Event-driven) — **When** 관리자가 강좌를 마감한 뒤 워커가 그 강좌의 미처리 `ENROLL` 요청을 처리하면, 워커는 각 요청의 결과를 `CLOSED`로 종결 **shall**하며 새 확정 레코드를 생성 **shall not**한다.
- **REQ-ADX-005** (State-driven) — **While** 대상 강좌의 모집 상태가 `CLOSED`이면, 워커는 `CAPACITY_INCREASE` 요청에 대해 어떤 대기자도 승격 **shall not**하고 `enrolled_count`를 변경 **shall not**하며, 결과를 `CLOSED`로 기록 **shall**한다 (§A.5). 대기명단 항목의 순번은 보존 **shall**된다.

### B.7 비기능 요구사항 (NFR)

- **REQ-NFR-001** (Ubiquitous) — 시스템은 동일 강좌에 대한 동시 다중 신청 부하 시나리오에서도 확정 인원이 정원을 초과하는 결과를 산출 **shall not**한다. 이 요구사항은 동시성 통합 테스트로 검증 **shall**된다.
- **REQ-NFR-002** (Ubiquitous) — 동시성·순서 보장 관련 통합 테스트는 **실제 PostgreSQL**(Testcontainers)에서 실행 **shall**되며, H2 등 인메모리 데이터베이스로 대체 **shall not**된다.
- **REQ-NFR-003** (Ubiquitous) — 모든 외부 입력은 서버 측에서 검증 **shall**되며, 클라이언트 측 검증만을 신뢰 **shall not**한다.
- **REQ-NFR-004** (Ubiquitous) — 워커는 각 요청의 처리 시작·종료·결과를 요청 식별자와 함께 추적 가능한 형태로 기록 **shall**한다.
- **REQ-NFR-005** (Ubiquitous) — 이 SPEC의 모든 인수 기준은 **Spring Boot 테스트만으로 검증 가능** **shall**해야 하며, 프론트엔드 구현을 전제 **shall not**한다.
- **REQ-NFR-006** (Ubiquitous) — 이 SPEC의 산출물은 커밋당 최소 커버리지 80%·전체 목표 85%를 충족 **shall**하며, LSP 에러·타입에러·린트에러를 0건으로 유지 **shall**한다.

> **개발 방법론(TDD RED-GREEN-REFACTOR)은 요구사항이 아니라 프로세스 제약이다.** "테스트를 먼저 작성했는가"는 산출물 관찰로 검증할 수 없으므로 요구사항으로 두면 추적성 매트릭스가 AC가 제공하지 않는 커버리지를 보고하게 된다. 이 지시는 plan.md §D 제약 조건 표로 이동했다.

### B.8 보유 내역 조회 (LST) — v0.3.0 개정

이 절은 v0.3.0 제자리 개정으로 **신설**되었다 (`## Amendments`, §A.6). 기존 절(B.1~B.7)의 요구사항은 한 건도 변경하지 않았으므로, 번호 재배치를 피하기 위해 B.7 뒤에 덧붙인다. `STS`와 별도 분류(`LST`)를 쓰는 이유는 대상 리소스가 다르기 때문이다 — `STS`는 **큐 요청 1건**의 처리 상태를 조회하고, `LST`는 **회원이 보유한 확정·대기 레코드 집합**을 조회한다.

- **REQ-LST-001** (Event-driven) — **When** 인증된 회원이 자신의 확정 수강신청 목록 조회를 요청하면, 시스템은 **그 회원의 활성 확정 수강신청**(`status='ENROLLED'`)만을 `enrollmentId` 오름차순으로 반환 **shall**하며, 각 항목에 §A.6.2가 정한 필드(`enrollmentId`·`courseId`·`courseTitle`·`status`·`enrolledAt`)를 포함 **shall**한다. 대상이 0건이면 404가 아니라 빈 목록과 200을 반환 **shall**한다.
- **REQ-LST-002** (Event-driven) — **When** 인증된 회원이 자신의 대기명단 항목 목록 조회를 요청하면, 시스템은 **그 회원의 활성 대기명단 항목**(`status='WAITING'`)만을 `position` 오름차순으로 반환 **shall**하며, 각 항목에 §A.6.2가 정한 필드(`waitlistEntryId`·`courseId`·`courseTitle`·`position`·`status`)를 포함 **shall**한다. 대상이 0건이면 404가 아니라 빈 목록과 200을 반환 **shall**한다.
- **REQ-LST-003** (Ubiquitous) — 두 목록 조회 API는 회원 식별자를 경로 변수·쿼리 파라미터·요청 본문 중 어떤 형태로도 입력받 **shall not**는다. 반환 집합은 오직 인증 주체에서 유도한 회원 식별자로 결정 **shall**되며, 어떤 요청 값을 조작해도 다른 회원의 확정 수강신청 또는 대기명단 항목이 반환 **shall not**된다 (§A.6.4).
- **REQ-LST-004** (Ubiquitous) — 두 목록 조회 API는 부작용 없는 읽기 전용 동작 **shall**이어야 하며, 호출 횟수와 무관하게 `enrollment`·`waitlist_entry`·`enrollment_request` 어느 테이블의 행도 생성·변경·삭제 **shall not**하고 `course.enrolled_count`를 변경 **shall not**한다. 이 API는 확정 경로가 아니다 (REQ-WRK-001, REQ-WRK-002, INV-ENR-002).
- **REQ-LST-005** (State-driven) — **While** 요청자가 인증되지 않은 상태이면, 두 목록 조회 API는 401을 반환 **shall**하며 어떤 회원의 보유 내역도 노출 **shall not**한다.
- **REQ-LST-006** (Ubiquitous) — 목록 조회가 반환한 `enrollmentId`는 `DELETE /api/enrollments/{enrollmentId}`가, `waitlistEntryId`는 `DELETE /api/waitlist-entries/{entryId}`가 받는 식별자와 **동일** **shall**하다. 즉 목록 조회의 응답만으로 취소 API 호출이 성립 **shall**하며, 클라이언트가 어떤 값을 추측·열거·유도해야 하는 상태가 남 **shall not**는다.

  > 이 요구사항이 개정의 **종결 조건**이다. REQ-LST-001·002가 식별자를 반환해도 그 값이 취소 API가 받는 값과 다르면 계약 공백은 그대로 남는다. AC-ENR-056이 조회 → 취소를 실제로 연결하여 이를 검증한다.

### B.9 큐 처리 실패의 진단 가능성 (DIAG) — v0.3.1 개정

이 절은 v0.3.1 제자리 개정으로 **신설**되었다 (`## Amendments` § 개정 2, §A.7). 기존 절(B.1~B.8)의 요구사항은 한 건도 변경하지 않았으므로, 번호 재배치를 피하기 위해 B.8 뒤에 덧붙인다. `NFR`과 별도 분류(`DIAG`)를 쓰는 이유는 대상이 다르기 때문이다 — REQ-NFR-004는 **정상 처리 흐름의 추적성**(시작·종료·결과)을 요구하고, `DIAG`는 **실패 경로의 원인 규명 가능성**을 요구한다. §A.7이 보인 대로 앞의 것을 충족해도 뒤의 것은 충족되지 않는다.

- **REQ-DIAG-001** (Event-driven) — **When** 큐 워커가 요청 처리 중 발생한 예외를 포착하면, 워커는 그 요청을 `FAILED`로 종결하기 전 또는 종결하는 동일한 처리 흐름 안에서 **예외의 타입·메시지·스택 트레이스**를 **요청 식별자**(`requestId`)와 **요청 종류**(`requestType`)와 함께 애플리케이션 로그에 기록 **shall**한다. 이 기록은 기본 로깅 설정에서 억제되지 않는 수준(`WARN` 이상)으로 남 **shall**는다.

  > 다섯 요소가 모두 필요한 이유: **타입**이 없으면 결함 계층(애플리케이션 / JDBC / 네트워크)을 구분할 수 없고, **메시지**가 없으면 같은 타입의 서로 다른 원인을 구분할 수 없으며, **스택 트레이스**가 없으면 예외가 발생한 지점을 특정할 수 없다. `requestId`·`requestType`이 없으면 그 실패가 어떤 요청의 것인지 대응시킬 수 없어 REQ-NFR-004가 이미 남긴 두 줄과 연결되지 않는다. 수준을 `WARN` 이상으로 못박는 이유는, 기본 설정에서 걸러지는 수준으로 기록하면 **기록했지만 보이지 않는** 상태가 되어 이 요구사항이 형식적으로만 충족되기 때문이다.
- **REQ-DIAG-002** (Ubiquitous) — 이 SPEC의 큐 처리 실패 경로에서 예외 객체를 포착한 뒤 그 예외에 대해 **어떤 기록도 남기지 않고 폐기**하는 프로덕션 코드 경로가 존재 **shall not**한다. 이 금지는 §A.7이 인용한 `drainQueue()`의 catch 블록에 한정 **shall not**되며, 실패 경로에 있는 모든 catch 블록에 적용 **shall**된다.
- **REQ-DIAG-003** (Ubiquitous) — 실패 진단 기록의 추가는 요청 처리의 **제어 흐름·트랜잭션 경계·종단 결과값**을 변경 **shall not**한다. 구체적으로 REQ-WRK-009(단일 요청의 실패가 큐 전체를 정지시키지 않음), REQ-WRK-010(요청 1건 = 트랜잭션 1개), 그리고 실패한 요청이 `state='DONE'`·`result='FAILED'`로 종결된다는 동작은 **그대로 유지 shall**된다.

  > 로깅은 관측 행위이지 제어 행위가 아니다. 이 요구사항이 없으면 M8 구현자가 예외를 기록하는 김에 재던지기·재시도·결과값 변경을 함께 넣어 **검증이 끝난 M1~M6의 실패 격리 설계를 흔들 수 있다.** AC-ENR-059가 로깅 추가 후에도 AC-ENR-016/017의 동작이 유지되는지를 같은 테스트에서 확인한다.
- **REQ-DIAG-004** (Event-driven) — **When** REQ-DIAG-001의 실패 진단 로깅이 반영된 뒤 실제 실패가 관측되면, 그 예외의 **타입 전체 이름·메시지 원문·스택 트레이스 상단 프레임**과, 그 원인이 **(a) 이 코드베이스가 소유한 애플리케이션 결함**인지 **(b) 이 코드베이스 밖의 외부·인프라 요인**인지의 **판정 및 그 판정 근거**가 `progress.md` §E.2 M8 절에 기록 **shall**된다. 이 기록은 (a)/(b) 어느 판정에서도 동일하게 이행 **shall**되며, 판정이 (b)라는 이유로 생략 **shall not**된다.

  > **REQ-DIAG-001과 무엇이 다른가 (plan-audit 1회차 지적 D5)**: REQ-DIAG-001은 실패 시점에 **로그가 남는가**(관측 수단의 확보)를 요구하고, 이 요구사항은 그렇게 남은 로그를 **실제로 읽고 판정하여 기록했는가**(관측의 실행과 그 결과의 보존)를 요구한다. 앞의 것은 M8 Step A로, 뒤의 것은 M8 Step B로 이행된다 (plan.md §F M8). 이 요구사항이 없으면 AC-ENR-061이 요구하는 조사·기록 의무를 뒷받침하는 §B 요구사항이 존재하지 않아, 인수 기준이 요구사항 없이 홀로 서게 된다. 분기 (a)/(b)의 **규범적 정의는 plan.md §F M8 Step B**이며, 그 정의는 예외의 **유래(origin)** 로 나뉘지 예외 클래스의 소속 패키지로 나뉘지 않는다 — JDK 패키지에 속한 예외라도 이 코드베이스의 로직이 유발했으면 (a)다.
  >
  > 이 요구사항은 문서 기록을 대상으로 하지만 **관찰 가능**하다 — REQ-WRK-015(워커 처리량 산출 근거의 문서 기록)가 이미 같은 형태의 선례다. 근본 원인의 **수정**을 요구하지 않는 이유는 AC-ENR-061의 근거 절에 있다.

## §C 시스템 불변식 (Invariants)

이 SPEC의 구현이 어떤 시점에도 위반해서는 안 되는 명제다. 각 불변식은 acceptance.md에서 기계적으로 검증된다.

| ID | 불변식 |
|---|---|
| INV-ENR-001 | 임의의 강좌에 대해 `유효한 확정 수강신청 행 수 = course.enrolled_count ≤ capacity`가 항상 성립한다. |
| INV-ENR-002 | `Enrollment` 레코드 생성과 `course.enrolled_count` 변경은 오직 큐 워커 처리 경로에서만 일어난다. |
| INV-ENR-003 | 동일 강좌·동일 회원에 대한 유효한 확정 수강신청은 최대 1건이다. |
| INV-ENR-004 | 동일 강좌 내 활성 대기 순번은 유일하며 결정적이다. |
| INV-ENR-005 | 큐의 한 요청이 실패해도 뒤따르는 요청의 처리가 중단되지 않는다. |
| INV-ENR-006 | 큐 행의 `state`는 `PENDING → DONE` 단방향이며 역전이가 없다. `result`는 `DONE` 전이 시 정확히 1회 설정되고 이후 변경되지 않는다 (§A.4 전이표). |
| INV-ENR-007 | 동일 강좌에 대해, 큐 행 순서값의 오름차순은 그 행들의 커밋 가시화 순서와 일치한다 (§A.2 접수 잠금의 결과). |
| INV-ENR-008 | 어떤 회원도 다른 회원의 확정 수강신청 또는 대기명단 항목을 취소할 수 없다. |
| INV-ENR-009 | 동일 강좌·동일 회원의 활성 대기명단 항목은 최대 1건이며, DB 제약이 이를 강제한다. |
| INV-ENR-010 | 어떤 회원도 다른 회원의 확정 수강신청 또는 대기명단 항목의 **식별자를 포함한 정보를 조회할 수 없다.** 보유 내역 조회 API는 회원 식별자를 입력으로 받지 않으므로 이 성질이 검사가 아니라 구조로 보장된다 (§A.6.4, v0.3.0 개정). INV-ENR-008이 쓰기(취소) 쪽을, 이 불변식이 읽기 쪽을 담당한다. |
| INV-ENR-011 | 결과가 `FAILED`인 큐 요청은 그 실패를 유발한 예외의 **타입·메시지·스택 트레이스를 애플리케이션 로그만으로 규명할 수 있다.** 예외를 기록하지 않은 채 `FAILED`로 종결되는 경로는 존재하지 않는다 (§A.7, v0.3.1 개정). INV-ENR-005가 실패의 **격리**를, 이 불변식이 실패의 **관측 가능성**을 담당한다. |

## §D 범위 제외 (Exclusions)

아래 항목은 이 SPEC의 범위에 포함되지 않는다(out of scope). 구현 중 "있으면 좋을 것 같아서" 추가하는 것을 명시적으로 금지한다.

### Out of Scope — 외부 인프라 도입

- Redis 원자적 카운터 기반 정원 관리
- 메시지 브로커(RabbitMQ / Kafka) 기반 큐
- 강좌 행(row)에 대한 직접적 비관적/낙관적 락을 **정원 관리의 주 메커니즘**으로 사용하는 방식

  위 3개는 사용자가 **명시적으로 배제**한 대안이다. 구현 단계에서 "더 낫다"는 판단으로 무단 대체하는 것을 금지한다. **DB 테이블 기반 순차 큐 처리 방식이 확정 설계다.** §A.2의 접수 잠금은 정원 관리가 아니라 **접수 순서 확정**만을 담당하는 별개의 장치이며, 정원 검사는 여전히 워커가 수행한다.

### Out of Scope — 다중 워커 인스턴스 운영

- 2개 이상 워커 인스턴스에서의 순서 보장
- 워커 리더 선출, 분산 락, 파티셔닝

  v1은 단일 워커 인스턴스를 전제한다 (REQ-WRK-012). REQ-WRK-013은 다중 인스턴스에서 **중복 처리만** 막을 뿐 순서를 보장하지 않는다.

### Out of Scope — 결제

- 수강료 결제 연동(PG사 연동, 결제 승인·취소·환불)
- 결제 상태에 따른 수강신청 확정 조건 분기
- 영수증·정산 기능

### Out of Scope — 비동기 알림 채널

- 이메일 발송(신청 결과 메일), 푸시 알림 / SMS
- WebSocket·SSE 기반 실시간 상태 푸시 (v1은 short-polling으로 대체)

### Out of Scope — 관리자 대리 조작

- 관리자에 의한 타 회원 수강신청 대리 취소
- 관리자에 의한 대기 순번 수동 조정

  v1의 취소 권한은 본인에게만 부여된다 (REQ-CNL-004). 대리 취소가 필요해지면 감사 로그 요구사항과 함께 별도 SPEC으로 도입한다.

### Out of Scope — 보유 내역 조회의 확장 (v0.3.0 개정)

- 종단 상태(`CANCELLED`·`PROMOTED`·`DUPLICATE`) 항목을 포함한 **이력 조회**
- 페이지네이션·정렬 옵션·기간/강좌 필터 등 조회 파라미터
- 관리자가 **타 회원의** 보유 내역을 조회하는 경로
- 확정·대기 목록을 한 응답으로 합치는 통합 엔드포인트

  §A.6.1이 정한 2종 엔드포인트가 `DEP-2` 계약 공백을 닫는 **최소 형태**다. 위 항목은 전부 "있으면 좋을 것 같아서"에 해당하며, 필요해지면 별도 SPEC으로 도입한다. 특히 관리자 타인 조회는 REQ-CNL-004(관리자 대리 조작 없음)와 같은 이유로 배제한다 — 도입한다면 감사 로그 요구사항이 함께 와야 한다.

### Out of Scope — 실패 진단의 확장 (v0.3.1 개정)

- 구조화 로깅(JSON 로그) 프레임워크 도입, 로그 수집·집계 파이프라인 구축
- 외부 APM·에러 트래커(Sentry 등) 연동
- `FAILED` 요청의 자동 재시도·데드레터 큐·수동 재처리 API
- 관리자용 실패 요청 조회 화면 또는 API
- **근본 원인이 이 코드베이스 밖(네트워크·커넥션 풀러·DB 인프라)으로 판정된 경우, 그 외부 요소 자체의 개선·우회·재시도 정책 도입**

  §B.9가 요구하는 것은 **"실패의 원인을 로그로 알 수 있게 한다"** 뿐이다. 위 항목은 전부 그 위에 얹는 운영 기능이며, 필요해지면 별도 SPEC으로 도입한다. 특히 마지막 항목은 M8 Step B의 판정이 (b) 외부 요인으로 나왔을 때 구현자가 "이왕이면 재시도도 넣자"로 범위를 넓히는 것을 명시적으로 금지한다 — 외부 요인에 대한 조치는 진단 결과의 기록으로 종결한다.

### Out of Scope — 프론트엔드 구현

- React 애플리케이션 스캐폴딩, 폴링 UI, 상태 표시 컴포넌트

  이 SPEC은 백엔드 API 계약과 정합성 보장까지를 범위로 한다. 후속 `SPEC-FRONTEND-001`(**계획 단계 진행 중** — v0.3.0 개정 시점 기준)이 이 SPEC의 접수·상태 조회·보유 내역 조회·취소 API를 소비할 예정이다. 이 SPEC의 인수 기준은 React 없이 100% 검증된다.

## §E 성공 기준

1. 정원 N인 강좌에 동시 5N건의 신청을 발생시키는 통합 테스트에서, 확정 인원이 정확히 N이고 초과가 0건이다 (INV-ENR-001).
2. 위 테스트에서 확정된 회원 집합이 접수 순서 상위 N명과 일치한다 (REQ-WRK-003, INV-ENR-007).
3. 접수 잠금을 제거하면 2번이 실패한다는 사실이 테스트로 확인된다 — 즉 순서 보장이 우연이 아니라 메커니즘의 결과임이 입증된다.
4. 확정자 1명이 취소하면 대기 1순위가 같은 트랜잭션에서 자동 승격되고, 그 사이에 접수된 신규 신청자가 대기자를 앞지르지 않는다 (REQ-WL-004).
5. 타인의 확정 수강신청을 취소할 수 없다 — API 계층과 워커 계층 양쪽에서 차단된다 (INV-ENR-008).
6. 동일 회원이 같은 강좌의 활성 대기 순번을 2개 이상 점유할 수 없고(INV-ENR-009), 부적격 대기자가 승격 대상이 되어도 큐가 멈추지 않고 다음 대기자가 승격된다 (REQ-WL-009).
7. `CLOSED` 강좌에서 취소는 정상 처리되지만 어떤 대기자도 승격되지 않는다 (REQ-WL-011, REQ-ADX-005).
8. 동시 접수 500건 부하에서 마지막 요청까지 5초 이내에 종단 결과에 도달한다 (REQ-STS-003).
9. 전체 테스트 커버리지 85% 이상, LSP 에러·타입에러·린트에러 0건.
10. (v0.3.0 개정) 회원이 자신의 보유 내역을 조회하여 얻은 `enrollmentId`·`waitlistEntryId`로 **추측이나 열거 없이** 취소 API를 호출할 수 있고, 그 조회에 다른 회원의 데이터가 섞이지 않는다 (REQ-LST-006, INV-ENR-010).
11. (v0.3.1 개정) 큐 요청이 `FAILED`로 종결되면 **로그만 보고** 그 실패를 일으킨 예외의 타입·메시지·발생 지점을 알 수 있고, 그 로깅 추가로 실패 격리(REQ-WRK-009)와 처리 원자성(REQ-WRK-010)의 동작은 달라지지 않는다. 나아가 그 로그로 실제 실패를 판정한 결과와 근거가 progress.md에 남는다 (REQ-DIAG-001~004, INV-ENR-011).
