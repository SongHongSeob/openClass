# SPEC-ENROLLMENT-001 — 인수 기준 (acceptance)

모든 인수 기준은 **자동화된 Spring Boot 테스트로 관찰 가능**해야 한다. "빠르게 느껴진다", "잘 동작한다" 같은 주관적 판정은 인수 기준이 될 수 없다. 프론트엔드 없이 100% 검증된다.

**검증 환경 전제 (협상 대상 아님)**: 모든 통합 테스트는 **실제 PostgreSQL**(Testcontainers)에서 실행한다. H2 대체 시 권고 잠금·`SKIP LOCKED`·부분 유니크 인덱스·CHECK 제약이 재현되지 않아 이 SPEC의 핵심 검증이 전부 무력화된다 (research.md §6).

**워커 구동 방식**: 테스트는 스케줄러 자동 실행에 의존하지 않고 워커 처리 루프를 명시적으로 호출한다. 타이밍 의존 테스트는 이 SPEC에서 인수 기준이 될 수 없다.

## §D.1 인수 기준

### 접수 및 접수 순서 보존

**AC-ENR-001** — 접수는 큐 적재만 수행 · 심각도: 필수
- **Given** 정원이 이미 가득 찬 강좌가 있을 때
- **When** 인증 회원이 접수 API를 호출하면
- **Then** 요청은 거부되지 않고 202(또는 200)와 요청 식별자를 반환하며, `enrollment_request`에 `state='PENDING'`·`result=NULL`인 행이 1건 생성되고, **응답 시점에 `enrollment` 행과 `course.enrolled_count`가 전혀 변하지 않는다.** 연속 3건 접수 시 순서값이 단조 증가한다.
- 대응: REQ-QUE-001, REQ-QUE-002

**AC-ENR-002** — 미인증 접근 차단 · 심각도: 필수
- **Given** `Authorization` 헤더가 없는 클라이언트일 때
- **When** 접수·상태 조회·취소 API를 각각 호출하면
- **Then** 모두 401이 반환되고 `enrollment_request` 행 수가 증가하지 않는다.
- 대응: REQ-QUE-006

**AC-ENR-003** — 존재하지 않는 강좌 접수 · 심각도: 필수
- **Given** 존재하지 않는 강좌 식별자가 주어졌을 때
- **When** 인증 회원이 접수 API를 호출하면
- **Then** 404가 반환되고 `enrollment_request` 행이 생성되지 않는다.
- 대응: REQ-QUE-005

**AC-ENR-004** — 요청 종류 도메인 제한 · 심각도: 필수
- **Given** 큐 테이블 스키마가 적용되어 있을 때
- **When** `request_type`을 §A.4에 없는 값(`PROMOTE` 등)으로 직접 INSERT하면
- **Then** 제약 위반으로 거부된다. 접수·취소·정원 증설 경로가 만드는 행의 `request_type`은 각각 `ENROLL`·`CANCEL`·`CAPACITY_INCREASE`다.
- 대응: REQ-QUE-007

**AC-ENR-005** — 접수 잠금이 순서값 할당에 선행 (구조적 검증) · 심각도: 필수
- **Given** 접수 서비스 구현 코드가 주어졌을 때
- **When** 접수 트랜잭션 경로에서 권고 잠금 획득 호출과 큐 행 INSERT 호출의 실행 순서를 검사하면
- **Then** 동일 트랜잭션 내에서 잠금 획득이 INSERT보다 **앞선다**. 또한 잠금 획득 없이 큐 행을 INSERT하는 프로덕션 경로가 0건이다.
- 검증 방법: 소스 검색(ast-grep) + ArchUnit 규칙 + 해당 지점 `@MX:ANCHOR` 주석 존재 확인
- 대응: REQ-QUE-003

**AC-ENR-006** — 커밋 지연 하에서의 순서 보존 (핵심) · 심각도: **필수 — 이 SPEC의 단일 관문 ①**
- **Given** 정원 1인 강좌와 회원 X·Y가 있고, 테스트가 JDBC 커넥션 2개로 접수 트랜잭션을 수동 제어할 수 있을 때
- **When** X의 접수 트랜잭션을 먼저 시작하여 커밋을 **지연**시킨 상태에서 Y의 접수 트랜잭션을 시작·커밋하려 시도하고, 이어서 워커를 큐가 빌 때까지 구동하면
- **Then** Y의 접수 트랜잭션은 X가 커밋할 때까지 접수 잠금에서 대기하므로 **Y의 순서값이 X보다 크고**, 확정된 1명은 **X**다. Y의 결과는 `WAITLISTED`다.
- 대응: REQ-QUE-004, INV-ENR-007

**AC-ENR-007** — 잠금 제거 대조군 (메커니즘 유효성 입증) · 심각도: **필수**
- **Given** 접수 잠금을 비활성화한 테스트 전용 구성이 주어졌을 때
- **When** AC-ENR-006과 동일한 커밋 역전 시나리오를 실행하면
- **Then** 순서 보장이 **깨진다** (Y가 확정되고 X가 대기로 밀린다). 즉 AC-ENR-006의 통과가 우연이 아니라 접수 잠금의 결과임이 입증된다.
- 근거: 이 대조군이 없으면 AC-ENR-006이 결함을 재현하지 못한 채 통과했을 가능성을 배제할 수 없다 (research.md §6-4).
- 대응: REQ-QUE-003

### 확정 경로 단일성

**AC-ENR-008** — 워커 외 경로의 도메인 무변화 (행동적 검증) · 심각도: **필수**
- **Given** 강좌·회원·기존 확정 수강신청이 준비되어 있고 `enrollment` 행 수와 `course.enrolled_count`를 기록해 두었을 때
- **When** **워커를 한 번도 구동하지 않은 상태**에서 접수 API·취소 API·관리자 강좌 수정(정원 증설) API를 각각 호출하면
- **Then** `enrollment` 행 수와 `course.enrolled_count`가 **최초 기록값과 정확히 동일**하다. 변한 것은 `enrollment_request` 행 수뿐이다.
- 근거: 이 단언은 JPA 연쇄 저장·`merge`·변경 감지 등 **정적 검색으로 잡히지 않는 우회 경로까지** 포착한다 (design.md §5).
- 대응: REQ-WRK-001, REQ-WRK-002, INV-ENR-002

**AC-ENR-009** — 우회 경로 봉쇄 (매핑·구조적 검증) · 심각도: 필수
- **Given** 구현 코드베이스와 JPA 메타모델이 주어졌을 때
- **When** (i) `Enrollment`를 대상으로 하는 연쇄 저장 설정(`CascadeType.PERSIST`/`ALL`)을 메타모델에서 조회하고, (ii) `EnrollmentRepository` 및 `Enrollment` 애그리게이트를 참조하는 패키지 목록을 검사하면
- **Then** (i) 결과가 0건이고, (ii) 참조 패키지가 워커 처리 패키지(및 읽기 전용 조회 패키지)로 한정된다. 컨트롤러·접수 서비스·취소 서비스·관리자 서비스는 포함되지 않는다.
- 검증 방법: JPA 메타모델 단언 + ArchUnit 규칙
- 대응: REQ-WRK-001, INV-ENR-002

### 워커 처리

**AC-ENR-010** — 정원 초과 0건 (동시성 부하) · 심각도: **필수 — 이 SPEC의 단일 관문 ②**
- **Given** 정원 10인 강좌와 서로 다른 회원 50명이 주어졌을 때
- **When** 50개 스레드가 `CountDownLatch`로 동시에 접수 API를 호출하고, 워커를 큐가 빌 때까지 구동하면
- **Then** 해당 강좌의 `status='ENROLLED'` 행이 **정확히 10건**이고, `course.enrolled_count = 10`이며 (두 값이 서로 일치), 나머지 40건의 결과가 `WAITLISTED`다. 초과 확정은 0건이다.
- 대응: REQ-WRK-004, REQ-WRK-005, REQ-NFR-001, INV-ENR-001

**AC-ENR-011** — 선착순 순서 일치 · 심각도: 필수
- **Given** AC-ENR-010과 동일한 상황에서
- **When** 큐 처리가 완료되면
- **Then** 확정된 10명의 회원 집합이 `enrollment_request.id` 오름차순 상위 10건의 회원 집합과 **정확히 일치**한다.
- 대응: REQ-WRK-003

**AC-ENR-012** — 정원 1 경계 · 심각도: 필수
- **Given** 정원이 **1**인 강좌와 회원 2명이 주어졌을 때
- **When** 두 회원이 동시에 접수하고 워커를 구동하면
- **Then** 확정이 정확히 1건이고 `enrolled_count = 1`이며, 나머지 1건은 `WAITLISTED`다. 확정된 회원은 순서값이 더 작은 쪽이다.
- 근거: off-by-one 결함이 가장 잘 드러나는 경계다.
- 대응: REQ-WRK-004, REQ-WRK-005

**AC-ENR-013** — 마감 강좌 요청 종결 · 심각도: 필수
- **Given** 큐에 `PENDING` `ENROLL` 요청 3건이 남아 있는 강좌를 관리자가 마감했을 때
- **When** 워커를 구동하면
- **Then** 3건 모두 결과가 `CLOSED`가 되고, 새 `enrollment` 행이 생성되지 않으며 `enrolled_count`가 변하지 않는다. 대기명단 항목도 생성되지 않는다.
- 대응: REQ-WRK-006, REQ-ADX-004

**AC-ENR-014** — 중복 신청 거부 · 심각도: 필수
- **Given** 회원 A가 강좌 C에 이미 확정되어 있을 때
- **When** A가 C에 다시 접수하고 워커를 구동하면
- **Then** 해당 요청의 결과가 `REJECTED`이고, A의 C에 대한 `ENROLLED` 행은 여전히 1건이며 `enrolled_count`가 증가하지 않는다. 또한 A가 미처리 `PENDING` 요청을 가진 상태에서 다시 접수해도 두 번째 요청이 `REJECTED`가 된다.
- 대응: REQ-WRK-007, INV-ENR-003

**AC-ENR-015** — 중복 확정 DB 제약 · 심각도: 필수
- **Given** 회원 A가 강좌 C에 확정되어 있을 때
- **When** 애플리케이션 계층을 우회하여 A·C의 `status='ENROLLED'` 행을 하나 더 직접 INSERT하면
- **Then** DB 제약 위반 예외가 발생하고 행이 생성되지 않는다.
- 대응: REQ-WRK-008

**AC-ENR-016** — 단일 요청 실패가 큐를 멈추지 않음 · 심각도: 필수
- **Given** 큐에 요청 3건이 있고 두 번째 요청이 처리 중 예외를 유발하도록 구성되었을 때
- **When** 워커를 구동하면
- **Then** 두 번째 요청만 결과 `FAILED`로 종결되고, 첫 번째와 **세 번째 요청이 정상적으로 종단 결과에 도달**한다. 세 번째 요청이 `PENDING`으로 남지 않는다.
- 대응: REQ-WRK-009, INV-ENR-005

**AC-ENR-017** — 처리 원자성 및 실패 기록 보존 · 심각도: 필수
- **Given** 확정 처리 도중(확정 행 INSERT 이후, 커밋 이전) 예외를 유발하도록 구성된 요청이 있을 때
- **When** 워커를 구동하면
- **Then** 도메인 변경이 롤백되어 `enrollment` 행 수와 `enrolled_count`가 변하지 않고, **동시에** 해당 큐 행은 `state='DONE'`·`result='FAILED'`로 남는다 (`PENDING`으로 되돌아가 무한 재시도되지 않는다).
- 대응: REQ-WRK-010

**AC-ENR-018** — 재처리 멱등성 및 상태 단방향성 · 심각도: 필수
- **Given** 이미 `state='DONE'`·`result='SUCCESS'`인 요청이 있을 때
- **When** 워커 처리 루프를 강제로 1회 더 실행하고, 이어서 해당 행을 `state='PENDING'`으로 되돌리는 UPDATE를 애플리케이션 경로로 시도하면
- **Then** `enrollment` 행 수와 `enrolled_count`가 증가하지 않고 `result`가 변하지 않으며, 역전이를 수행하는 프로덕션 코드 경로가 0건이다.
- 검증 방법: 통합 테스트 + 소스 검색(ast-grep)
- 대응: REQ-WRK-011, INV-ENR-006

**AC-ENR-019** — 단일 워커 인스턴스 전제 명시 · 심각도: 필수
- **Given** 구현과 배포 설정이 주어졌을 때
- **When** 스케줄러 활성화 지점과 배포 문서를 검사하면
- **Then** 워커 스케줄러를 활성화하는 지점이 1개소이고, 단일 인스턴스 전제가 README 또는 배포 문서에 명시되어 있으며, 다중 인스턴스에서 순서 보장이 성립하지 않는다는 경고가 함께 기록되어 있다.
- 대응: REQ-WRK-012

**AC-ENR-020** — 행 점유 배타성 · 심각도: 필수
- **Given** 큐에 `PENDING` 행이 있을 때
- **When** 두 개의 동시 트랜잭션이 각각 클레임 쿼리(`FOR UPDATE SKIP LOCKED`)를 실행하면
- **Then** 동일한 행 식별자가 양쪽에서 동시에 반환되지 않는다.
- 대응: REQ-WRK-013

**AC-ENR-021** — DB 정원 제약이 최종 방어선 · 심각도: 필수
- **Given** 정원 5, 확정 인원 5인 강좌가 있을 때
- **When** 애플리케이션 로직을 우회하여 `enrolled_count`를 6으로 갱신하려 시도하면
- **Then** DB 제약 위반 예외가 발생하고 갱신이 거부된다.
- 대응: REQ-WRK-014

**AC-ENR-022** — 워커 설정값 산출 근거 기록 · 심각도: 필수
- **Given** 구현이 완료되었을 때
- **When** 워커의 폴링 주기·배치 크기 설정값과 문서를 대조하면
- **Then** 두 설정값이 design.md §6의 산출표와 일치하거나, 어긋나는 경우 **실측치에 근거한 개정 기록**이 progress.md §E.2에 남아 있다.
- 대응: REQ-WRK-015

**AC-ENR-023** — 배치 크기 초과 요청의 순서 보존 · 심각도: 필수
- **Given** 정원 5인 강좌에 워커 배치 크기보다 많은 수의 요청이 순서대로 접수되어 있을 때
- **When** 워커를 큐가 빌 때까지 구동하면 (여러 배치에 걸쳐 처리된다)
- **Then** 확정된 5명이 순서값 상위 5건과 일치하고, 대기 순번도 접수 순서와 일치한다.
- 대응: REQ-WRK-003

### 상태 조회

**AC-ENR-024** — 종단 상태 및 대기 순번 조회 · 심각도: 필수
- **Given** 회원이 접수하여 요청 식별자를 받았을 때
- **When** 상태 조회 API를 호출하면
- **Then** 워커 구동 전에는 `PENDING`이 반환되고, 워커 구동 후에는 §A.4의 종단 결과값 중 하나가 반환된다. 결과가 `WAITLISTED`인 경우 대기 순번이 함께 반환된다.
- 대응: REQ-STS-001

**AC-ENR-025** — 타인 요청 조회 차단 · 심각도: 필수
- **Given** 회원 A의 요청 식별자가 있을 때
- **When** 회원 B가 그 식별자로 상태를 조회하면
- **Then** 403 또는 404가 반환되고 응답 본문에 A의 요청 정보(회원 식별자·강좌 식별자·상태)가 포함되지 않는다.
- 대응: REQ-STS-002

**AC-ENR-044** — 승격 대상자의 중복 확정 방지 및 **큐 생존성** · 심각도: 필수
- **Given** 강좌 X(정원 2, 확정 2명 A·B)에 활성 대기자 C(순번 1)·D(순번 2)가 있고, **C는 X에 이미 유효한 확정을 보유한 부적격 상태**일 때 (REQ-WRK-007의 3번 검사 도입 이전에 적재된 항목 또는 직접 INSERT로 재현한다)
- **When** A가 취소하여 워커가 그 `CANCEL` 요청을 처리하면
- **Then** 아래를 **모두** 만족한다.
  1. C에 대한 중복 확정 행이 생성되지 않고, C의 대기 항목이 `status='DUPLICATE'`(spec.md §A.4.3)로 종결되어 다시 대기 선두에 남지 않는다.

  3. **해당 `CANCEL` 요청의 결과가 `CANCELLED`다** (`FAILED`가 아니다). A의 취소가 소실되지 않는다.
  4. 이어서 또 다른 `CANCEL`을 처리해도 동일하게 정상 종결된다 — 큐 선두가 막히지 않는다.
- 근거 (2차 감사 E1): 이전 판의 Then은 "중복 행이 생성되지 않는다"만 요구했다. 그런데 **확정 INSERT가 부분 유니크 인덱스에 걸려 트랜잭션 전체가 롤백되는 경로**도 그 조건을 만족한다 — 중복 행은 확실히 안 생긴다. 그러나 그 경로에서는 취소가 소실되고 여유 정원이 영원히 재배정되지 않으며 부적격 항목이 큐 선두에 남아 **이후 모든 `CANCEL`을 같은 방식으로 실패시킨다.** 2·3·4번이 그 실패 경로를 배제한다.
- 대응: REQ-WRK-008, REQ-WL-009, INV-ENR-003

### 중복 대기 방지 및 마감 강좌 처리 (2차 감사 E1·E2 반영)

**AC-ENR-050** — 동일 회원 중복 대기 거부 (2계층) · 심각도: 필수
- **Given** 회원 A가 정원이 가득 찬 강좌 C에 접수하여 워커 처리가 끝나 **활성 대기자(`WAITING`)가 된 상태**일 때 (A의 이전 큐 행은 `state='DONE'`이다)
- **When** (i) A가 C에 **다시 접수**하고 워커를 구동하고, 이어서 (ii) 애플리케이션 계층을 우회하여 A·C의 `status='WAITING'` 대기 항목을 하나 더 직접 INSERT하면
- **Then** (i)의 결과는 `REJECTED`이고 C에 대한 A의 활성 대기 항목은 **여전히 1건**이며 대기 순번이 새로 부여되지 않는다. (ii)는 **DB 제약 위반 예외**로 거부되고 행이 생성되지 않는다.
- **또한** A가 자신의 대기를 취소한 뒤 다시 접수하면 정상 접수된다 — 부분 유니크 인덱스가 `WHERE status='WAITING'`으로 필터링되므로 취소·승격 완료 항목은 재신청을 막지 않는다.
- 근거 (2차 감사 E1): 이전 판의 중복 검사는 확정·미처리 큐 요청 2종만 보았다. 대기 상태의 회원이 조급하게 재신청하는 것은 **평범한 사용자 행동**이며, 그 결과 동일 회원이 같은 강좌의 대기 순번 2개를 점유해 선착순 공정성이 훼손되고 승격 시 큐 선두가 막힌다 (AC-ENR-044 참조).
- 검증 방법: 통합 테스트(API + 워커) + `JdbcTemplate` 직접 INSERT (Testcontainers PostgreSQL)
- 대응: REQ-WRK-007, REQ-WL-010, INV-ENR-009

**AC-ENR-051** — 부적격 대기자 건너뛰기 (정원 증설 경로) · 심각도: 필수
- **Given** 강좌 X(정원 2, 확정 2명)에 활성 대기자 C(순번 1, **X에 이미 확정 보유 — 부적격**)·D(순번 2)·E(순번 3)가 있을 때
- **When** 관리자가 정원을 4로 증설하고 워커가 `CAPACITY_INCREASE` 요청을 처리하면
- **Then** C는 건너뛰어져 `status='DUPLICATE'`(spec.md §A.4.3)로 종결되고, **D와 E가 순번 오름차순으로 승격**되어 `enrolled_count = 4`가 되며, 결과가 `PROMOTED`다 (`FAILED` 아님). C에 대한 중복 확정 행은 생성되지 않는다.
- 근거: 승격 루프가 부적격 대기자에서 예외를 던지면 정원 증설 전체가 롤백되어 **증설분이 아무에게도 배정되지 않는다.** AC-ENR-044가 `CANCEL` 경로를, 이 AC가 `CAPACITY_INCREASE` 경로를 각각 검증한다 — 두 경로가 같은 승격 헬퍼를 쓰더라도 분기 진입 조건이 달라 별도 검증이 필요하다.
- 대응: REQ-WL-009

**AC-ENR-052** — 마감 강좌에서의 취소: 취소 허용·승격 동결 · 심각도: 필수
- **Given** 강좌 X(정원 2, 확정 2명 A·B, 활성 대기 C·D)가 있고 관리자가 X를 **마감(`CLOSED`)** 했을 때 (삭제 요청도 `CLOSED` 전이다 — `SPEC-COURSE-001` REQ-ADM-008)
- **When** A가 취소하고 워커가 그 `CANCEL` 요청을 처리하면
- **Then** A의 확정이 취소 상태로 전이되고 `enrolled_count`가 1로 감소하며 결과는 `CANCELLED`다. **그러나 C는 승격되지 않는다** — 새 `enrollment` 행이 생성되지 않고 C·D의 대기 항목 상태와 순번이 **그대로 보존**된다.
- 근거 (2차 감사 E2): `CLOSED`는 "새 확정 수강신청을 받지 않는다"는 뜻이고 승격도 새 확정을 만드는 행위다 (spec.md §A.5). 승격을 허용하면 관리자가 삭제했다고 믿는 강좌에 확정자가 계속 생긴다. 반대로 취소까지 막으면 회원이 강좌에서 빠져나올 수 없게 되므로 취소는 허용한다.
- 대응: REQ-WL-011

**AC-ENR-053** — 마감 강좌에서의 정원 증설: 승격 없음 · 심각도: 필수
- **Given** AC-ENR-052와 같은 마감(`CLOSED`) 강좌에 활성 대기자가 존재할 때
- **When** `CAPACITY_INCREASE` 요청이 적재되어 워커가 처리하면
- **Then** 결과가 `CLOSED`이고, 새 `enrollment` 행이 0건이며 `enrolled_count`가 변하지 않고, 모든 대기 항목의 상태와 순번이 보존된다.
- **또한** 관리자가 그 강좌를 다시 `OPEN`으로 되돌린 뒤 정원 증설을 재요청하면 대기자가 순번 오름차순으로 정상 승격된다 — 대기명단이 마감으로 파괴되지 않았음을 확인한다.
- 대응: REQ-ADX-005

## §D.4 완료 정의 (Definition of Done)

아래 항목이 **모두** 충족되어야 이 SPEC이 완료로 전이될 수 있다. §D.1의 모든 AC는 심각도 "필수"이므로 예외 없이 전부 통과해야 한다 — 미충족 항목을 사유 기록으로 대체하는 경로를 두지 않는다.

- [ ] §D.1의 AC-ENR-001 ~ AC-ENR-053이 **전부 통과**한다.
- [ ] 단일 관문 2건이 실제 PostgreSQL 환경에서 통과한다: **AC-ENR-006**(커밋 지연 하 순서 보존), **AC-ENR-010**(정원 초과 0건).

- [ ] **AC-ENR-008**(워커 미구동 시 도메인 무변화)이 통과한다 — 확정 경로 단일성이 정적 검색이 아니라 DB 상태로 입증된다.
