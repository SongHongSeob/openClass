# SPEC-ENROLLMENT-001 — 구현 계획 (plan)

> **읽는 순서 안내**: §C는 **되돌리기 어려운 순서**로 배치했다. §C.2(접수 순서 보장)와 §C.3(취소·승격 원자성)이 이 SPEC의 핵심이며, 최초 감사에서 지적된 두 개의 치명적 결함을 각각 닫는다. 리뷰는 §C.2 → §C.3 → §C.4 순으로 집중하는 것이 효율적이다.

## §A 배경 (Context)

- 3분할된 SPEC 중 **세 번째이자 마지막**이다. 실행 순서: `SPEC-AUTH-001` → `SPEC-COURSE-001` → **`SPEC-ENROLLMENT-001`**.
- **선행 의존: `SPEC-AUTH-001`, `SPEC-COURSE-001`.** 두 SPEC이 모두 `completed`가 되기 전에는 run 단계에 진입하지 않는다.
- 이 SPEC은 프로젝트의 **유일한 고난도 영역**이다. 앞의 두 SPEC은 표준 CRUD에 가까워 리스크가 낮았고, 남은 예산 전부를 여기의 동시성 검증에 투입하는 것이 분할의 목적이었다.
- 미해소 클래리피케이션 마커: **0건**.

### C.2 접수 순서 보장 — 이 SPEC의 1번 결정 (감사 D1)

**문제**: PostgreSQL 시퀀스는 INSERT 시점에 비트랜잭션적으로 할당되지만 행의 가시성은 커밋 시점에 결정된다. 따라서 `id` 순서와 커밋 순서가 어긋날 수 있고, 워커가 "보이는 것만" 처리하면 나중 접수자가 먼저 확정될 수 있다. `SKIP LOCKED`는 **잠긴 행**을 건너뛸 뿐 **보이지 않는 행**에는 무력하다 (research.md §2·§3).

**해결**: 접수 트랜잭션이 `[강좌 단위 권고 잠금 획득 → 큐 행 INSERT → 커밋]` 순서를 지킨다. `pg_advisory_xact_lock`은 트랜잭션 범위이므로 커밋·롤백 시 자동 해제되며 해제 누락이 구조적으로 발생하지 않는다.

**정합성 논증** (전문은 research.md §4):

동일 강좌의 두 접수 트랜잭션 `T₁`, `T₂`에서 임계 구간 `[잠금 획득 → 커밋]`은 배타적이므로 겹치지 않는다. `T₁`이 먼저 잠금을 얻으면 `T₁`은 순서값 `s₁`을 할당하고 커밋하면서 잠금을 놓고, `T₂`는 그 이후에 `s₂`를 할당한다. 시퀀스가 단조 증가하므로 `s₁ < s₂`이면서 `commit(T₁) < commit(T₂)`다. 따라서 **강좌별로 순서값 순서 = 커밋 순서**이고, 워커에게 보이는 집합은 언제나 접수 순서의 **접두사**다. 순서값이 큰 행은 보이는데 작은 행이 안 보이는 상태가 존재할 수 없다.

**비용**: 잠금이 강좌 단위이므로 다른 강좌의 접수는 완전히 병렬이다. 임계 구간은 INSERT 1건으로 밀리초 미만이다. 강좌당 잠금 1개만 획득하고 중첩하지 않으므로 순환 대기(교착)가 성립하지 않는다.

**배제된 대안과의 구별 (중요)**: 사용자가 배제한 것은 "강좌 행에 대한 직접 락 기반 **정원 관리**"다. 이 접수 잠금은 정원을 관리하지 않는다 — **접수 번호표 발급**만 직렬화하고, 정원 검사와 확정은 여전히 워커가 수행한다. DB 테이블 큐 + 워커 아키텍처는 그대로 유지된다. 이 구별은 research.md §4에 표로 정리되어 있으며, 구현 중 이 경계를 넘는 변경(예: 접수 시점에 정원을 검사하여 즉시 확정)은 §G 안티패턴이다.

**잠금이 걸리는 범위 — 큐 적재 3종 전부 (2회차 감사 후속 N2)**: 접수 잠금은 `ENROLL`뿐 아니라 `CANCEL`·`CAPACITY_INCREASE` 적재 경로에도 동일하게 적용된다. REQ-QUE-004의 가시화 순서 보장이 "동일 강좌의 **큐 행**" 전체에 대한 명제이기 때문이다 — 한 종류라도 잠금 없이 적재되면 그 종류의 행에서 순서값 순서와 커밋 순서가 어긋나 §C.2의 논증이 성립하지 않는다. AC-ENR-005는 처음부터 "잠금 없이 큐 행을 INSERT하는 프로덕션 경로 0건"이라는 3종 전부의 조건을 검증하고 있었고, REQ-QUE-003의 문구만 "접수 트랜잭션"으로 좁게 적혀 있었다. v0.2.2에서 요구사항을 **AC 쪽으로 확장**하여 정합을 맞췄다(AC를 축소하지 않았다) — 잠금은 설계상 이미 균일하게 획득되고 있고, 축소하면 REQ-QUE-004가 `CANCEL`·`CAPACITY_INCREASE` 행에 대해 검증 수단을 잃기 때문이다. `ENROLL`과 `CANCEL`의 **상대 순서** 자체는 §C.3의 원자적 취소·승격 설계 덕분에 결과에 영향을 주지 않지만(AC-ENR-031 양방향 사례), 그것은 "순서가 뒤집혀도 괜찮다"는 것이지 "가시화 순서 보장이 필요 없다"는 뜻이 아니다.

**검증**: AC-ENR-005(구조) + AC-ENR-006(커밋 지연 시나리오) + **AC-ENR-007(잠금 제거 대조군)**. 대조군이 특히 중요하다 — 잠금을 껐을 때 순서가 실제로 깨져야만 AC-ENR-006의 통과가 증거로서 의미를 갖는다. 대조군이 함께 통과해버리면 테스트가 결함을 재현하지 못한다는 뜻이다.

**전제 명시**: 이 보장은 **워커 인스턴스 1개**를 전제한다. 최초 설계는 이 전제를 계획 문서에만 적었으나, 이번에는 **요구사항(REQ-WRK-012)으로 승격**하고 AC-ENR-019가 문서화 여부까지 검증한다.

### C.3 취소·승격 원자성 — 2번 결정 (감사 D2)

**문제**: 최초 설계는 취소 API가 확정 레코드를 즉시 취소하고 `enrolled_count`를 감소시킨 뒤 별도 `PROMOTE` 작업을 큐에 넣었다. 그 사이에 **여유 정원이 노출되는 틈**이 생긴다. 대기자 C·D가 있는 상태에서 신규 신청자 E의 큐 행이 `PROMOTE` 행보다 앞선 순서값을 가지면, 워커가 E를 먼저 처리하여 **E가 C·D를 앞지른다.** 선착순 정합성을 표방하는 시스템에서 대기자를 뒤로 밀어내는 결함이다.

**해결**: 취소를 `CANCEL` 큐 작업으로 만들고, 워커가 **한 트랜잭션 안에서** `[확정 취소 → enrolled_count 감소 → 대기 1순위 즉시 승격]`을 연속 수행한다. 감소가 커밋되는 시점에는 승격도 이미 커밋되어 있으므로 **여유 정원이 외부에 노출되는 시간 창이 존재하지 않는다.**

이로써 `enrolled_count`를 변경하는 경로가 **워커 1개소로 실제로 수렴**한다. 최초 설계의 "모든 경로가 워커로 수렴한다"는 주장은 요구사항이 뒷받침하지 않았다 — 이번에는 REQ-WRK-002가 명시적으로 그것을 요구하고, AC-ENR-008이 DB 상태로 검증한다.

**검증**: AC-ENR-030(승격 발생) + **AC-ENR-031(대기자 우선 배정)**. AC-ENR-031은 `ENROLL`과 `CANCEL`의 순서값 전후를 **양방향으로** 테스트한다 — 어느 순서든 결과가 같아야 틈이 없다는 증명이 된다.

### C.4 확정 경로 단일성의 검증 방법 — 3번 결정 (감사 D4)

**문제**: "확정 경로가 1개소"는 이 SPEC의 1차 방어선이지만 **코드 구조에 의존**하므로 가장 쉽게 무너진다. 그런데 최초 설계는 이를 `grep "save"`로 검증했다. JPA에서는 연쇄 저장(`cascade`)·`merge`·변경 감지로 **`save` 호출 문자열 없이도** 행이 생성된다. 검사가 통과하면서 방어선이 사라질 수 있었다.

**해결 — 3층 검증** (design.md §5):

1. **매핑 제약** — `Enrollment`를 대상으로 하는 `CascadeType.PERSIST`/`ALL`이 0건임을 JPA 메타모델로 단언한다.
2. **아키텍처 규칙(ArchUnit)** — `EnrollmentRepository`·`Enrollment` 애그리게이트 참조 패키지를 워커 처리 패키지(및 읽기 전용 조회)로 한정한다.
3. **행동 검증(AC-ENR-008)** — 워커를 구동하지 않은 상태에서 접수·취소·정원 증설 API를 호출한 뒤 `enrollment` 행 수와 `enrolled_count`가 **전혀 변하지 않았음**을 DB에서 직접 단언한다.

3번이 결정적이다. 1·2번은 **알려진** 우회로를 막고, 3번은 **모르는** 우회로까지 잡는다. 어떤 경로로 우회하든 DB 상태 단언은 깨진다.

### C.5 취소 소유권 검증 — 보안 (감사 D12)

**문제**: 최초 설계의 취소 요구사항은 "취소가 접수되면"이라고만 쓰여 **누가** 취소할 수 있는지를 제약하지 않았다. 인증만 통과하면 타인의 확정 수강신청 식별자로 취소를 호출할 수 있고, 식별자는 순차값이라 열거 가능하다. 모든 요구사항을 만족하면서 타인을 강제 탈락시키고 그 자리를 다음 대기자에게 넘길 수 있었다 — OWASP A01 접근 통제 결함이다.

**해결 — 2층 방어**:

- **1차 (API 계층, REQ-CNL-002)**: 취소 API가 요청자와 확정 레코드 소유자를 비교하고 불일치 시 403/404를 반환하며 **큐 행을 적재하지 않는다.**
- **2차 (워커, REQ-CNL-003)**: 워커가 `CANCEL` 처리 시 소유권을 **다시** 검증하고 불일치 시 `REJECTED`로 종결한다.

2차가 필요한 이유: 접수와 처리 사이에 시간 간격이 있고, 큐 행을 직접 조작하는 경로가 생길 가능성에 대비한다. AC-ENR-037이 우회 적재 시나리오로 이 2차 방어선을 직접 검증한다.

**관리자 대리 취소는 제공하지 않는다** (REQ-CNL-004). 대리 취소는 감사 로그·사유 기록 등 부수 요구사항을 동반하므로 v1에 넣지 않고, 필요해지면 별도 SPEC으로 도입한다. AC-ENR-038이 그런 엔드포인트가 없음을 확인한다.

### C.6 워커 처리량과 지연 목표 — (감사 D5)

**문제**: 최초 설계는 `fixedDelay=500ms` × 배치 50건 = **100건/초**로 구성하고 "정상 부하에서 5초 이내"를 요구했으나 "정상 부하"를 정량화하지 않았다. 그런데 SPEC이 스스로 밝힌 동기 시나리오는 "신청 개시 시각에 다수 동시 도착"이다. 3,000건이 몰리면 마지막 요청은 30초 — **문서화된 설정 자체가 요구사항을 6배 위반**하고 있었고, 어떤 AC도 이를 잡지 못했다 (기존 지연 AC는 요청 1건만 폴링했다).

**해결** (산출표는 design.md §6):

| 항목 | 값 |
|---|---|
| 폴링 주기 | 200ms |
| 배치 크기 | 200건 |
| 이론 처리량 | 1,000건/초 |
| 보수적 처리량 (이론값의 50%) | 500건/초 |
| A — 접수 측 직렬화 지연 (§C.2 접수 잠금) | **추정** ≤ 0.5초 (미실측 — research.md §7 V5가 측정) |
| B — 워커 소진 지연 | 1.0초 (500 ÷ 500건/초) |
| C — 폴링 대기 | 0.2초 |
| **부하 상한 (REQ-STS-003)** | **동시 접수 500건** → 종단 **A+B+C ≈ 1.7초** (5초 목표 대비 여유 3.3초) |

> **종단 예산은 design.md §6이 SSOT다.** REQ-STS-003의 5초는 "요청 접수 시점부터 종단 결과 확정까지"이므로 예산에 **접수 측(A)** 이 포함되어야 한다. A항은 §C.2의 접수 잠금이 도입되면서 생긴 항으로 2차 감사(E4)에서 추가되었는데, 위 표는 그때 갱신되지 않아 워커 측(B+C)만 더한 1.2초로 남아 있었다 — 2회차 감사 지적 N3의 세 번째 항목이다. 두 문서 모두 5초 목표를 만족하므로 요구사항 위반은 아니며, 이 개정은 수치 정합만 맞춘 것이다.

상한을 초과하면 지연이 큐 깊이에 비례해 선형 증가한다. 이 특성을 감추지 않고 REQ-STS-003 후단과 API 문서에 명시한다.

**실측 우선 원칙**: 위 숫자는 계산값이다. AC-ENR-026이 **부하 상한에서 직접 측정**하며, research.md §7 V5/V6에서 실제 처리량을 잰다. 실측이 계산과 어긋나면 **요구사항의 숫자를 실측에 맞게 개정한다** — 측정을 요구사항에 맞추지 않는다. 개정 시 근거를 progress.md §E.2에 기록한다.

### C.7 프론트엔드 — 이 SPEC 범위 밖

- 사용자 결정(**백엔드 우선**)에 따라 React 스캐폴딩을 생성하지 않는다.
- 모든 인수 기준은 Spring Boot 테스트만으로 검증 가능하며, AC-ENR-048이 이를 기계적으로 확인한다.
- 후속 `SPEC-FRONTEND-001`(**계획 단계 진행 중** — v0.3.0 개정 시점 기준)이 이 SPEC의 접수·상태 조회·보유 내역 조회·취소 API를 소비하고 short-polling UI를 구현할 예정이다.
- CORS 설정은 프론트엔드 착수 시점에 실제 오리진이 정해진 뒤 추가한다.

### C.8 보유 내역 조회 엔드포인트 — v0.3.0 개정의 유일한 설계 결정 (M7)

> **이 개정에서 되돌리기 가장 어려운 결정이자 가장 바뀔 가능성이 높은 결정이다** — 공개 API 표면이고 후속 `SPEC-FRONTEND-001`이 곧 소비하기 때문이다. 개정 리뷰는 여기에 집중하는 것이 맞다. 결정의 규범적 형태는 spec.md §A.6에 있고, 여기에는 **판단과 근거**를 적는다.

**결정 1 — 목록 조회 2종 (`GET /api/enrollments/mine`, `GET /api/waitlist-entries/mine`)**

| 후보 | 평가 |
|---|---|
| **목록 조회 2종 (채택)** | 취소 경로와 리소스 접두사가 일치해 조회↔취소 대응이 경로만 보고 드러난다. 각 엔드포인트가 이미 그 리소스를 소유한 컨트롤러(`EnrollmentController`·`WaitlistController`)에 자연히 들어가 새 컨트롤러·새 패키지가 필요 없다 |
| `EnrollmentStatusResponse`에 식별자 2개 추가 | 기각. 변경량은 최소지만 **`requestId`를 보관 중인 클라이언트만** 취소할 수 있다. 새 탭·다른 기기 사용자는 여전히 취소 불가 — 공백이 절반만 닫힌다 |
| 통합 엔드포인트 1종 (`GET /api/members/me/enrollments`가 확정+대기를 함께 반환) | 기각. 두 리소스가 서로 다른 패키지(`enrollment`·`waitlist`)에 있어 한 컨트롤러가 양쪽을 조립하면 §7 패키지 경계를 가로지른다. 응답 형태도 이질적 항목의 합집합이 되어 클라이언트 분기가 늘어난다 |
| `/api/me/...` 새 접두사 | 기각(약한 기각). 동작은 동등하나 기존 경로 체계에 없던 최상위 접두사를 새로 만들 이득이 없다 |

**결정 2 — 인가 규칙을 추가하지 않는다**

두 경로 모두 `SecurityConfig`의 `permitAll` 매처(`/api/auth/**`, `GET /api/courses`·`/api/courses/*`)와 `hasRole("ADMIN")` 매처(`/api/admin/**`) 어디에도 걸리지 않으므로 **기존 `anyRequest().authenticated()` 기본 규칙이 그대로 적용**된다. `SecurityConfig`는 이 SPEC의 PRESERVE 대상이며, M7은 그 파일을 **열 이유가 없다.** REQ-LST-005(401)는 새 코드가 아니라 기존 기본 규칙으로 충족된다 — 다만 AC-ENR-057이 그 사실을 실측한다.

**결정 3 — `courseTitle`은 별도 조회로 채우고, `Enrollment`→`Course` 연관을 만들지 않는다**

`courseTitle` 표시를 위해 `Enrollment`에 `@ManyToOne Course`를 추가하는 것은 **금지한다** (§G 안티패턴에 추가). 이유는 성능이 아니라 **안전**이다 — `Enrollment`를 향한 JPA 연관을 만드는 순간 연쇄 저장·변경 감지 우회 경로가 열려 §C.4가 세운 3층 검증(특히 AC-ENR-009 (i) 연쇄 저장 0건)의 전제가 흔들린다. 대신 조회 서비스가 `courseId` 집합을 모아 기존 `CourseRepository`로 한 번 더 읽어 합친다. 회원 1명의 보유 건수는 작으므로 비용도 문제되지 않는다.

**결정 4 — 배치 위치**

- 확정 목록: `enrollment.query` 패키지의 읽기 전용 조회 서비스 + `EnrollmentController`. `enrollment.query`는 design.md §7이 이미 "읽기 전용" 용도로 만든 패키지이고, AC-ENR-009 (ii)의 허용 목록("워커 처리 패키지 **및 읽기 전용 조회 패키지**")에 이미 포함되어 있다 — **ArchUnit 규칙을 고칠 필요가 없다.**
- 대기 목록: `waitlist` 패키지(`WaitlistService` 계열) + `WaitlistController`. `waitlist`는 "순번 관리와 조회만 담당하고 `Enrollment`를 생성하지 않는다"는 design.md §7의 규정에 그대로 부합한다.

**결정 5 — 반환 범위는 활성만, 정렬은 규범**

근거는 spec.md §A.6.2 / §A.6.3에 있다. 정렬을 명세에 못박은 이유는 AC가 순서를 단언할 수 있어야 하기 때문이며, 이는 이 SPEC이 처음부터 지켜온 "주관적 판정은 인수 기준이 될 수 없다" 원칙의 연장이다.

M1~M6은 **완료 상태이며 이 마일스톤은 그 위에 읽기 전용 조회만 얹는다.** 배경은 §A.3, 설계 결정은 §C.8, 규범적 계약은 spec.md §A.6에 있다.

- `GET /api/enrollments/mine` — 본인 활성 확정(`ENROLLED`) 목록, `enrollmentId` 오름차순 (`enrollment.query` + `EnrollmentController`)
- `GET /api/waitlist-entries/mine` — 본인 활성 대기(`WAITING`) 목록, `position` 오름차순 (`waitlist` + `WaitlistController`)
- 응답 항목에 **행 식별자**(`enrollmentId` / `waitlistEntryId`)를 포함 — `requestId`도 `position`도 아니다 (§C.8 결정 1)
- `courseTitle`은 기존 `CourseRepository`로 별도 조회하여 합친다 — `Enrollment`에 JPA 연관 추가 **금지** (§C.8 결정 3)
- 소유권 범위 한정은 `Authentication` 유도 회원 식별자 **단독**으로 — 회원 식별자를 받는 핸들러 파라미터를 만들지 않는다 (spec.md §A.6.4)
- `SecurityConfig`·워커·큐·승격 헬퍼·`enrolled_count` 경로는 **열지 않는다** (§C.8 결정 2, §A.3)
- 대응 요구사항: REQ-LST-001 ~ REQ-LST-006, INV-ENR-010
- 대응 AC: AC-ENR-054 ~ AC-ENR-058
- **M7 완료 조건**: **AC-ENR-056**(조회 → 취소 계약 폐쇄)과 **AC-ENR-057**(미인증 차단 및 타인 데이터 격리)이 **함께** 통과한다. AC-ENR-054/055가 각각 통과해도 AC-ENR-056이 실패하면 반환된 식별자가 취소 API가 받는 값과 대응하지 않는다는 뜻이므로 `DEP-2` 공백은 닫히지 않은 것이며 M7은 미완료다. 추가로 **AC-ENR-058**(무부작용)이 통과하여 이 개정이 INV-ENR-002를 훼손하지 않았음이 DB 상태로 입증되어야 한다.
- **회귀 조건**: M7은 기존 파일 중 `EnrollmentController`·`WaitlistController`·두 저장소 인터페이스를 건드리므로, M1~M6의 해당 테스트(접수/상태 조회/취소/대기 순번/ArchUnit 경계)를 재실행하여 무손상을 확인한다.

## §G 안티패턴 (구현 중 금지)

| 안티패턴 | 왜 금지인가 |
|---|---|
| 접수 API에서 정원을 검사하고 즉시 확정 | REQ-WRK-001 / INV-ENR-002 위반. 확정 경로가 2개가 되는 순간 정원 초과 경로가 열린다. 접수 API는 **잠금 잡고 큐에 넣기만** 한다 |
| 접수 잠금을 순서값 할당 **이후에** 획득 | §C.2의 정합성 논증이 성립하지 않는다. 순서 보장이 조용히 사라지고 테스트는 대부분 통과한다 — 최악의 실패 형태다 |
| 접수 잠금을 "성능상 불필요해 보인다"며 제거 | 감사 D1이 정확히 그 상태였다. 제거하려면 AC-ENR-007 대조군이 여전히 실패함을 먼저 설명해야 한다 |
| 취소 API에서 직접 `enrolled_count` 감소 또는 승격 | REQ-WRK-002 / REQ-WL-004 위반. 여유 정원 노출 창이 생겨 신규 신청자가 대기자를 앞지른다 (감사 D2) |
| 취소와 승격을 서로 다른 큐 작업으로 분리 | 위와 동일. 두 작업 사이에 다른 요청이 끼어든다 |
| 소유권 검증 없이 취소 처리 | REQ-CNL-002/003 위반. 타인 강제 탈락(IDOR) — 보안 결함 (감사 D12) |
| 확정 경로 단일성을 소스 `grep`만으로 검증 | JPA 연쇄 저장·`merge`·변경 감지로 우회된다 (감사 D4). DB 상태 단언(AC-ENR-008)이 반드시 함께 있어야 한다 |
| `Course`에서 `Enrollment`로 연쇄 저장 설정 | 위 우회 경로를 직접 만드는 행위 |
| 배치 전체를 한 트랜잭션으로 처리 | REQ-WRK-009 / INV-ENR-005 위반. 1건 실패가 배치를 전부 롤백시킨다 |
| `FAILED` 기록을 실패한 트랜잭션 안에서 수행 | 기록까지 롤백되어 요청이 `PENDING`으로 남고 **무한 재시도**가 된다 (research.md §5) |
| 폴링과 1건 처리를 같은 빈에 두기 | 자기 호출은 프록시를 거치지 않아 `@Transactional`이 적용되지 않는다. 스타일이 아니라 정확성 문제다 |
| `PROCESSING` 중간 상태 추가 | 멈춘 행을 복구할 스위퍼가 필요해진다. 행 잠금으로 충분하다 (spec.md §A.4) |
| 통합 테스트를 H2로 대체 | 권고 잠금이 아예 없어 §C.2 메커니즘을 재현할 수 없다. 검증이 무력화된다 |
| 동시성 테스트를 단일 스레드 반복문으로 작성 | 경쟁 조건을 재현하지 못한다. 실제 스레드 풀 + `CountDownLatch`가 필요하다 |
| 지연 목표 테스트를 요청 1건 폴링으로 작성 | 부하와 무관한 값을 재게 된다. 감사 D5가 이 형태로 놓쳤다. 부하 상한에서 측정한다 (AC-ENR-026) |
| 실측이 요구사항과 어긋날 때 측정 조건을 완화 | 순서가 반대다. **요구사항의 숫자를 실측에 맞게 개정**하고 근거를 기록한다 |
| 워커 인스턴스를 2개 이상 구동 | REQ-WRK-012 위반. `SKIP LOCKED`가 중복 처리만 막고 순서는 보장하지 않는다 |
| 배제된 대안(Redis/브로커/강좌 행 직접 락 정원 관리)으로 무단 대체 | 사용자가 명시적으로 배제한 설계다. 변경하려면 SPEC 개정이 선행되어야 한다 |
| 승격 시 부적격 대기자에서 예외를 던져 트랜잭션을 롤백 | REQ-WL-009 위반. 취소가 소실되고 여유 정원이 재배정되지 않으며, 그 항목이 대기 선두에 남아 **이후 모든 `CANCEL`을 같은 방식으로 실패시킨다** — 큐 선두 영구 정지 (감사 E1). 확정 INSERT **앞에서** 적격성을 검사하고 부적격 항목은 종결 후 건너뛴다 |
| 중복 검사를 확정·미처리 큐 요청 2종으로만 구성 | REQ-WRK-007 위반. 이미 대기자인 회원의 재신청이 통과하여 같은 강좌의 대기 순번을 2개 점유한다 (감사 E1). 활성 대기 항목 보유 검사가 3번째로 반드시 있어야 하며, DB 부분 유니크 인덱스가 backstop이다 |
| `CANCEL`·`CAPACITY_INCREASE` 처리에서 강좌 모집 상태를 확인하지 않음 | REQ-WL-011 / REQ-ADX-005 위반. `SPEC-COURSE-001`은 강좌 삭제를 `CLOSED` 전이로 처리하므로(REQ-ADM-008), 상태 확인이 없으면 **관리자가 삭제했다고 믿는 강좌로 대기자가 승격된다** (감사 E2). 정책은 spec.md §A.5에 확정되어 있다 — 취소는 허용, 승격은 동결 |
| 마감을 이유로 확정 취소 자체를 거부 | 위 정책의 반대편 오류. 회원이 강좌에서 빠져나올 수 없게 된다. `CLOSED`가 막는 것은 **새 확정**이지 취소가 아니다 (spec.md §A.5) |
| React 스캐폴딩 생성 | 사용자 결정(백엔드 우선) 위반. spec.md §D 범위 제외 |
| **(M7)** 보유 내역 조회에 회원 식별자 파라미터를 두고 소유권을 "검사"로 막기 | REQ-LST-003 / INV-ENR-010 위반. 검사는 실수 한 번으로 뚫리지만 **입력이 없으면 뚫릴 것이 없다.** `DEP-2` 조사가 "사용자 직접 입력" 우회안을 기각한 이유가 열거 표면 제공이었는데, 그 대체물이 같은 표면을 다시 만들면 개정의 목적이 사라진다 (spec.md §A.6.4) |
| **(M7)** `courseTitle`을 위해 `Enrollment`에 `@ManyToOne Course` 연관을 추가 | §C.4의 3층 검증 전제를 무너뜨린다. `Enrollment`를 향한 JPA 연관은 연쇄 저장·변경 감지 우회 경로를 여는 행위이며, AC-ENR-009 (i)이 금지한 것과 같은 종류다. 기존 `CourseRepository`로 별도 조회해 합친다 (§C.8 결정 3) |
| **(M7)** `waitlistEntryId` 자리에 `position`을, `enrollmentId` 자리에 `requestId`를 반환 | REQ-LST-006 위반이자 이 개정 전체의 무력화. `position`은 강좌 내 순번이고 `requestId`는 큐 테이블의 독립 시퀀스다 — 둘 다 취소 API가 받는 값이 아니다. AC-ENR-056이 이 혼동을 정확히 판별한다 |
| **(M7)** 조회 API에 인가 규칙·`SecurityConfig` 수정 추가 | 불필요하며 PRESERVE 위반이다. 두 경로는 어떤 `permitAll` 매처에도 걸리지 않아 기존 `anyRequest().authenticated()`가 이미 401을 낸다 (§C.8 결정 2) |
| **(M7)** 조회 범위를 넓혀 이력·페이지네이션·필터를 함께 구현 | spec.md §D "보유 내역 조회의 확장" 범위 제외 위반. 개정의 목적은 취소 대상 지목이라는 **최소 형태의 계약 폐쇄**이며, 그 이상은 별도 SPEC이다 |
