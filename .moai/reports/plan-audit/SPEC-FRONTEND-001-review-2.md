**N1. WAITLIST-ORDER-SEMANTICS-FALSE — `spec.md`:L245, `plan.md`:L350, `spec.md`:L98 — The SPEC asserts that the mine-waitlist list's `position` ascending order "means the promotion order", which is false whenever a member is waitlisted in more than one course. — Severity: major — Required fix:** `spec.md:245` (REQ-CNL-008 rationale) states "특히 대기 목록의 `position` 오름차순은 **승격 예정 순서**를 그대로 의미하므로, 클라이언트가 재정렬하면 사용자가 자신의 대기 순서를 오해한다", and `plan.md:350` M6 item 4 repeats it as an implementation directive ("대기 목록의 순서는 **승격 예정 순서**를 의미한다"). Source verification contradicts this: `WaitlistEntry.java` declares a **course-scoped** position — its class javadoc names the partial unique index `(course_id, position) WHERE status='WAITING'` and states that `WaitlistEntryRepository#nextPosition` computes "강좌 전체 이력의 최대 순번 + 1", i.e. per course. `WaitlistEntryRepository:56` `findByMemberIdAndStatusOrderByPositionAsc(memberId, …)` therefore sorts a **cross-course** result set by a **per-course** rank: a member holding position 1 in course A and position 2 in course B gets A-then-B, which encodes nothing about which will be promoted first (the two queues are independent and promotion is driven by each course's own capacity events). The normative requirement itself (REQ-CNL-008: display in backend order, do not re-sort) is correct and harmless and should be kept; the **rationale and the M6 directive are the defect**, and they matter because this SPEC's own blocker-grade principle is that the screen must not tell the user something untrue (`acceptance.md:162`, INV-FE-004 family). An implementer following `plan.md:350` literally would label the list "승격 예정 순서" in the UI. Fix: rewrite both rationales to state the true reason — the backend order is deterministic and re-sorting would desynchronize the displayed order from the response the AC compares against (AC-FE-110) — and add an explicit note that `position` is a **rank within its own course** and MUST be rendered adjacent to `courseTitle`, never as a global queue position.
